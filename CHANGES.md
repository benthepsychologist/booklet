# Changes to the booklet format

What changed in each version of the format, newest first. `SPEC.md` states the rules as they are now and carries no history; this file keeps it. Section numbers are those of `SPEC.md`. A version marked "wording only", "drawing only", "the reference renderer only" or "wording and the reference renderer" changed no file: the marker stayed as it was.

## Changes from v0.16

The format becomes 0.17 and the renderer 0.17.0 (released 2026-10-30).

- **Pages: a tree inside a tab** (section 3, "Pages: a tree inside a tab"; section 4). A page line, `> [!page|id parent:x icon:name] Title`, starts a named page in a tab: an activity holds tabs, a tab holds pages, and a thematic break splits a page into `***` sections (in 0.15 and 0.16 it was called a page break and a page had no name). A tab with no page line is one page, as every activity in use today is. The rules (ids, `parent:`, reading order, where a page line may stand, Back and Next, the counter) are in section 3. A menu of the pages, a search and a list of the pages that link to the one on show are a renderer's, and the format defines no syntax for them. Where the pages design was silent the rules follow what the Obsidian plugin (0.8.0) chose.
- **A first word that holds `:` is a setting** (section 4). On every kind, so `> [!page|parent:map] Title` is a page with no written id under `map`. Ids never hold `:`, so nothing that was an id is lost; on a kind that needs an id the line gets the report for a missing id in place of the report for an invalid one. (The Obsidian plugin applies it to page lines only; the two differ only on a line that is an error anyway.)
- **`parent:` leaves the activity line** (section 3, section 4's table). An activity no longer sits under another and a module is never a wiki. `parent:` on an activity line is an error in the linter, and a reader reports it as a setting the kind does not take and ignores it; there is no transition. The wiki of 0.16 becomes one activity whose pages are page lines; an activity that keeps entries cannot become a page and stays an activity, grouped by a module's tabs. This is the old "pages are pagination" rule turned round: in 0.15 and 0.16 a thematic break was called a page break and a page had no name; in 0.17 a thematic break splits a page into `***` sections and "page" means the named thing in the tree. Every file with a `***` keeps its meaning.
- **A `[!page]` line is a defined kind** (section 4). `> [!page] Title` was a reading callout of the author's own kind in 0.16; it is now a page line.
- **Design after the records** (section 8). Design written after the records region's closing `%%` is read as design, as it was, but a save now leaves it where it is, after the records, instead of moving it above them: a writer leaves everything it did not change as and where it was. The linter reports it once, with what it holds. A design after the region that ends inside a code fence that is never closed still fails the linter as an unclosed fence, but no longer gives a writer a reason to refuse the file, since nothing is moved into the fence; adding a region after a body that ends in such a fence may still be refused.
- **`description:`** (section 2). An optional front matter key: one sentence of plain words for whoever shows a description of the file (a search result, a link preview, the blurb of a card); without it a reader uses the first paragraph. The linter warns on an empty one and on one that starts a multi-line value.
- **`entries:folded`** (section 3, "Kept entries, folded"; section 4's table). A setting on a `repeat` activity's line that says its kept-entries list starts folded. The name is `entries:folded` and the place is the activity's own line; the plugin reads the mark in a later release, and a renderer that has no such fold ignores it and keeps it as written.
- **The marker is `booklet: "0.17"`** everywhere the format names its version, in the linter, `SKILL.md`, the examples and the test fixtures. The registry's modules are not re-marked here.

**Known, and left as it is in this version:**

- A thematic-break line alone on a line inside a `$$` display-math block: whether it splits a page is open (section 13).
- The pages design also makes a bare activity read only itself; this version does not change that rule.

**Not yet supported in the reference renderer.** The reference renderer draws a page tree with a trail above a page, Back, Up and Next, and cards for the pages under a page. It does not draw a menu of the pages, a search of the pages, a "Mentioned on" list of the pages that link to the one on show, or "Show N more" for a long row of child pages, and it no longer draws a module as a wiki (a tree of activities): `parent:` on an activity line is reported and ignored. The format defines no syntax for the menu, the search, the list or the button, so no file loses anything by their absence; a wiki written with `parent:` on activity lines loses its tree until its activities are made pages.

The marker is `booklet: "0.17"`. A file marked `"0.16"` opens with a notice; change its marker to `"0.17"`.

## Changes in v0.16.1: the reference renderer only

Nothing a file may say has changed: the marker stays `booklet: "0.16"`, and no file needs touching. The renderer is 0.16.1.

- **Add a module is refused where the module would land inside an unclosed code fence.** On a booklet whose body ends inside a code fence that never closes, a module put after that fence's opening line (at the end of the body) would be the fence's code, never a module. The reader is told why ("This booklet ends inside a code fence that is never closed, so a module cannot be added after it. Close the fence in Markdown first."), and nothing is changed. Before, the module was accepted with no problem reported, and was not read. Anywhere else a module is added as before: an update of a module the booklet has, in place; a new module put before a data section the fence is in; an update that closes the fence. A download that would write records after the body stays refused while the body ends inside the fence.
- **The browser's copy of such a booklet keeps its design, and the records kept beside it.** For a booklet whose design after its records ends inside an unclosed code fence, the copy the renderer keeps in the browser reads back the design as it was after a reload, a Rename or Remove a module, the white space at the end of the fence's last line included. Before, the design gained the records region's lines (`%%` and the records line) inside the author's code block. The records are kept beside the copy and read with it, so work kept as records for a module the design lacks (by a newer file that dropped the module, or the file's own) is kept by a later newer file too; before, that later file could drop it. A download that would write records after the body stays refused while the fence is open.
- **A store booklet's records kept as written are the reader's work.** When a newer file of a store booklet drops the module the reader answered in, reading it keeps that work as records kept as written under the module's records line. Before, if that was all the reader had kept, the next newer file of that booklet was drawn over the browser's copy with no offer, and the work was gone. Now the page offers to read it, as for any work the file lacks; reading it carries those records forward byte for byte, through any number of newer files; dismissing the offer leaves the copy as it was; a newer file that brings the module back shows the answer in it again. A host that saves them to the store keeps them in the file, which is then drawn as before.

## Changes from v0.15

The format becomes 0.16. The renderer is 0.16.0.

- **A span of days** (section 6, "A span of days, and summaries"; section 8). `limit: 7 days` keeps the entries of the past 7 days, today and the 6 dates before it, on every view; `limit: 1 day` is today's. `limit: 7` is still the newest 7. A day is defined once, in section 8: the calendar date of an entry's `ts` in the reader's own time zone, with "today" taken when the page is drawn, and `repeat daily` keeps one entry a day by the same day. An entry whose `ts` will not parse, or is in the future, is in no span. A `limit:` that is neither a positive whole number nor a number of days (`limit: week`) is ignored and reported, and is an error in the linter.
- **Summaries** (section 6; section 7's "Nothing is computed from it" names the one exception). `summary: on` turns a query's kept entries into summary rows, a dates row and one row per question with named statistics (`count`, `days`, `average`, `lowest`, `highest`, `total`, `most`), or one question's distribution, which every view draws as it draws any rows. Any other value (`summary: yes`) is ignored and reported, and is an error in the linter. A span or a summary on a data block, or on a question whose activity keeps no entries, is ignored and reported (the linter warns). The reference renderer reads the key but does not work out the rows yet: it shows a line saying summaries are not yet supported in place of the view (section 13).
- **`blue` and `purple`** (sections 6 and 7) are colour names beside `warm`, `green`, `amber`, `slate` and `teal`. Like `slate` and `teal`, they carry no tone. The reference renderer draws each in every theme and in print from that theme's own sky and lilac colours.
- **A question asked for each pick** (section 4's settings table; section 5, "A question asked for each pick"; sections 6 and 8). `each:<id>` on a question line names a `choice`, a `multi` or a widget in the same activity, its source, and the question is asked once for each pick in the source's answer. Its answer is a list of pairs, `{ "pick": …, "a": … }`; a pair whose pick is taken back is kept and not drawn. One level only. Nine kinds take `each:`: `text`, `lines`, `scale`, `matrix`, `date`, `choice`, `multi`, `number` and `widget`. An `each:` that names nothing, names its own question, names nothing in the activity, names a question of another kind or names a question that has `each:` of its own is ignored and reported, and is an error in the linter, which reports a chain once, on the line that names the follow-up; one placed before its source is a warning. The reference renderer draws such a question as its title and a line saying it is not yet supported, and keeps its pairs as written through opening, saving and Finalize (section 13).
- **Views of a follow-up** (section 6). A question asked for each pick is one field per pick, labelled "<title> · <pick's words>", in the source's order, in a card's lines, a kept entry's card, a table, a list, a `line` view and a summary's rows; `fields:` naming the follow-up names all of its fields. A follow-up named alone in `from:` gives one row per pick and value; the reference renderer gives one row per entry, with a field per pick, in `table`, `list` and `cards`, and in `tiles`, `bars` and `line` draws a line saying the view does not draw it yet.
- **An answer of the wrong shape is kept as written** (section 8, with a table of each kind's shape; section 12). An answer whose JSON type is not the one its kind stores (a `scale` answer of `1.5`, a `choice` answer that is an object) is kept exactly as written, in answers, drafts and kept entries: its question is drawn read-only with a notice, no press, Finalize or save changes it, a view leaves it out of its row, and the reader says once, among the file's problems, that answers are kept as written. An answer that holds nothing (`null`, `false`, a string of only white space, a list or object holding only such values) is no answer, never one of the wrong shape.
- **Words the reader wrote before** (section 4's settings table; section 5, "Words the reader wrote before"; section 7). In an activity that keeps entries, a reader's own options (`open`) were already offered again; the rule now says which words come back, from where, in what order and how many, and adds a body widget's words and, when its line asks, a `lines` question's earlier lines. A word typed in a `grid-select` cell and a `text` answer are not offered again. `earlier:<n>` (on `choice`, `multi`, `lines` and widget lines; digits only) sets how many are offered at each place, 12 by default; `earlier:0` offers none. Any other value is ignored and reported, and is an error in the linter, which also warns where `earlier:` can offer nothing (a `choice` or `multi` without `open`, a `readonly` or `grid-select` widget, or an activity that keeps no entries, unless the question is a body widget or asked for each pick, which offer words from the answer being written). The reference renderer honours `earlier:` for own options, newest first by the time in each entry's `ts`, leaving out today's daily entry and answers of the wrong shape; it does not yet offer a body widget's words or a `lines` question's earlier lines (section 13). Section 7 says when a typed word matches one of a widget's words.
- **A word typed in a grid cell leaves the answer's order as picked** (section 8). It goes at the end, and one taken out leaves the others where they were. The reference renderer does this too.
- **Records are written back as they were read** (section 8, "Writing records back"; section 12's writer line; section 3). A record the reader did not change is written back exactly as written: nothing re-sorted, nothing respaced. The permission to write a record with other spacing, or to sort a list of entries, is gone. The new part of section 8 sets out, for any writer, how the reader's change is made (one member of its block, or one item of its list, in that block's own layout), that the body comes back byte for byte with its trailing blank lines, that the file's line endings and a byte order mark are kept, where a new value, entry or block goes, that two regions are kept and not joined, and where writers may differ. Section 3 says the bare activities' records run from a plain records line to the next records line, wherever the plain line stands. The reference renderer now writes this way. Before, every save built the records region again (each block re-spaced, entries sorted by `ts`, two regions joined into one), trimmed the body's trailing blank lines and wrote a file with Windows line endings back with Unix ones.
- **A body that ends inside an unclosed code fence** (section 8). A records region added after such a body would be read as part of the fence, and its records would not be read back. A writer may refuse to add records to such a file and say why. The reference renderer now refuses: a download is not made, the host is not sent the change and `Booklet.text()` returns `""`, and the reader is told why ("This booklet ends inside a code fence that is never closed, so an answer cannot be written after it. Close the fence in Markdown first."). Nothing the reader did is cleared, and the fence is never closed for them. A booklet with nothing to write after its body is written as it was; one whose design after its records ends in such a fence is refused even unchanged, since writing it would move the records into the fence. The linter already reported such a fence as an error.
- **Words typed for an own option and not yet added** (section 5). With `open`, words typed in the field are added, as Enter or Add would add them, when the field is left and when the page is closed or reloaded; on a `choice` they replace the pick. Before, only Enter and Add added them.
- **The Booklet plugin for Obsidian exists** (sections 7, 10 and 13). `booklet-obsidian`, in pre-release, opens a booklet note in a Booklet view of its own and writes what the reader answers into the note's records by section 8's rules. It does not draw everything yet; what it leaves out it marks "Not yet supported" and keeps as written, and its own repository lists what it draws. Before, the spec said no plugin had been built.
- **Renderer fixes** (the reference renderer only; no rule changed). Printing an activity prints every tab under its name, every page and all its endnotes in one list, numbered by the whole activity; before, only the tab and the page on show were printed. "Read the newer file" keeps the work of a module the newer file removed or renamed as records in the booklet, with or without a host script, and it comes back as answers if a module of that id returns; before, without a host script, that work was hidden and never written to the file. Widgets: a `readonly` body widget with no figure names its places from its regions; a kept entry's card names a place's words ("Feet — Restless, Sore"); a word holding a comma stays one word; typing a word's label presses that word, and pressing it never adds it twice; a press right after typing in a widget's field lands; a widget's typed words are kept when the page is closed or reloaded. A folded group with no title is named by its first words, not "Note".
- **Save times** (the reference renderer only). Writing records back as written made saves slower on a large booklet, and the trim pass at the end of 0.16 took most of that back: a save to the browser's copy no longer runs the whole writer, and writing the file compares an untouched entry by its plain JSON first. On a made-up booklet of 30,000 kept entries (Node, the median of 7 runs), a save to the browser's copy takes 16.9 ms and the file's text 102 ms, against 10.9 ms and 38.6 ms in 0.15.0, and 69.5 ms and 178.5 ms before the trim.

**Known, and left as it is in this version:**

- The reference renderer does not yet draw summaries or questions asked for each pick, and does not offer a body widget's earlier words or a `lines` question's earlier lines (section 13).
- Printing a module's own screen with tabs prints only the tab on show; an activity prints whole.
- "Read the newer file" with no host script keeps a renamed module's work under its old id, so the renamed module shows none of it.
- A renderer served at `/app` with no slash reads its default folder at `/modules/`, by ordinary address rules; serve it at `/app/` or `/app/booklet.html` (README, `docs/hosting.md`).
- A page that drops a `booklet-store` tag it used to carry: the entries its readers opened from that store are not read from the default folder, and following the link opens the folder's file as a new entry beside the old one, which keeps its answers.
- The Obsidian plugin's 0.16 release follows separately, from its own repository.
- Planned for 0.17, each after its own design round: pages as a tree inside one tab of an activity, and a question that sorts items into bins.

The marker is `booklet: "0.16"`. A file marked `"0.15"` opens with a notice; change its marker to `"0.16"`.

## Changes from v0.13

The format becomes 0.15; no 0.14 was released. The renderer is 0.15.0.

- **Tabs** (section 3, "Tabs" and "A module's tabs"; section 4). A tab line, `> [!tab] Name` or `> [!tab|id] Name`, inside an activity starts a tab that runs to the next tab line or to the activity's end, for areas of one activity meant to be very different (a dashboard, a form and a reading). What comes before the first tab line is the activity's opening, shown above the tabs on every tab. A tab with no id takes its name as one (`What to change` is `what-to-change`; a name that leaves nothing is `tab-2` for the second tab). Tab lines in a module's opening declare the module's tabs, and an activity joins one with `tab:<id>` on its line; with none it is in the first. A tab is presentation: the activity keeps one set of answers whichever tab a question is on, and which tab is showing is never stored. A link to a tab's name opens that tab. `tab` is a kind that takes no settings, `tab:` is new on an activity line, and a row does not cross a tab line.
- **Pages are pagination** (section 3). A thematic break inside an activity or a tab is a page break, as before (not one inside a group, below), but a page now has no name, no id and no menu: a renderer moves through the pages with Back, "Page 2 of 3" and Next at the foot of the screen, and Next on the last page goes on to the next activity. Which page is showing is never stored. Before, a page was named by its first heading (or "Page 2") in a pages menu, and a link could open it by that name; a heading now names no page, and the reference renderer's pages menu is gone. The reference renderer's Next and Back land at the start of the part now on show, under the bar, past an opening drawn above it (an activity's opening above its tabs).
- **A group holds blocks** (section 6). In an activity, a `[!group]` callout's body is read as the activity's own text is, with one `>` less: prose, images, callouts, query views, and questions with their options, hints and solutions. A question in a group is written `> > [!choice|id] …`, its options `> - [ ] …` and its hint `> > [!hint]-`. Before, a group's body was one piece of Markdown, and a Booklet line in it was drawn as its raw text. A question in a group is its activity's like any other: its id is the module's, and its answer is stored, kept and sent as before, so ids, records and what the submit build sends are unchanged by a group, and it is read back wherever answers are: a query view, a kept entry's card, and adding a module, which renames a clashing id inside a group as it does outside one. A line that makes structure (`module`, `activity`, `tab`, `row`, `data`, `records`) cannot go inside a group: the renderer ignores and reports it, the linter refuses it. A thematic break inside a group is a rule drawn in it, not a page break. A group is drawn plain, under its title (before, an open group was drawn as a note, with the note's word and colour), and a folded one that holds an answer is drawn open. Outside an activity a group is a fold of Markdown, as before.
- **One at a time steps through groups** (section 12). The steps of the part on show (the activity, the tab, or one `***` section of either) are its groups, and the view is offered when it holds two or more; a step draws its group open. What comes before the first group is drawn whole above every step, whatever it is and however long; before, what came before the first question went with that question, so a problem statement or a key to a scale was gone from the second step on. It is drawn, not held: it scrolls with the rest. What comes between two groups goes with the group after it, and what follows the last with the last. **A part of questions in no group no longer offers the step view**: before, one at a time took any three or more questions one by one, and now a question in no group is never a step of its own. An author who wants them taken one at a time puts each question, or each set to take together, in a `> [!group] Title`, or gives them `***` sections of their own, which Back and Next turn. The steps' words are "Step 2 of 5" and "Next step". All at once, nothing changes.
- **A question in a row is read back** (the reference renderer only). A query view and a kept entry's card read a question in a row, as they read one in a group; before, they read only the questions outside every row, so a row's answers were kept but not shown.
- **A card's parts** (sections 3 and 4; "A card's picture" before). A card has a title, a picture, a blurb and a status line, each from the file or a default. The `>` lines directly under an activity line are the text of its card's status line (before, the reference renderer dropped them), and `status:off` on the line hides the status line. `status:` takes only `off`. The blurb is the activity's first paragraph, as before.
- **A reply for each option** (sections 4 and 5). A bullet nested under a `choice` or `multi` option (two spaces under `- [ ]`) is that option's reply, shown under the options when the reader picks it; a question that marks a correct answer shows its replies with its marks. A reply is content, not an answer: it is never stored or sent. Before, the reference renderer took a nested bullet for the end of the option list, and every later option was lost.
- **How a question is drawn follows one rule** (section 5). Its words keep a readable width, and short options sit beside them only when both fit, else under them (before, the reference renderer put them beside the words above 640 px). A matrix that does not fit its column as a grid is drawn as one single-choice question per item, with the same answer under the same key, so a window made narrower and wider again loses nothing; such an item is cleared by pressing its answer again. Drawn as separate questions, the matrix's stem (its own words, on its line) stays in view while its items are answered, held under the top of the screen until its last item (on a window too short to give the items room, a phone on its side, a renderer may let it scroll; the reference renderer does at 360 px tall or less); drawn as a grid, it is not held.
- **Images from the host's store or the default folder** (sections 6, 12 and 13). A relative image path may be read from a store the host declares or from the folder the host serves beside the renderer, and nowhere else; a conforming reader still fetches no remote image. The reference renderer now draws images for a booklet it opened from either, read relative to the booklet's own name, checked by path and by bytes, and only in a part of the booklet whose text is still the store's file's. Every other booklet keeps the quiet box and asks for nothing. The linter warns on a relative path the reference renderer would never read.
- **`readonly` and `describe` on `svg-regions`** (section 7). Both engines honour both, and a region may carry a `note`, which `describe` shows. Before, `svg-regions` ignored both.
- **Nothing folds that the author did not fold** (section 12). Reading mode, which folded a page into sections at its shallowest heading level, is gone from the reference renderer, and headings draw as headings. One switch, Open all, shows only on a screen holding callouts the author folded with `-`, and opens or folds exactly those, never a question's hint or solution.
- **The default folder** (section 12 and `docs/hosting.md`; no file changes). On a page served over http or https with no `booklet-store` tag, `#/open/<name>` reads `modules/<name>` beside the renderer, by the same reader and checks as a declared store, so a host can serve the released file unchanged. A declared store always wins, and `file:` is unchanged. A booklet from the folder is only read: it is never the host's (no `onChange`, and no Submit in the submit build), and "Your booklets" keeps it apart from a store booklet of the same name. A host's own policy header needs `'self'` in `connect-src` for the read. `tools/verify-renderer.py` (new) checks a copy, by its path or its address, against a release's `sha256`.
- **Contents lists** (the reference renderer; no rule changed). A booklet's modules, a module's activities, a wiki's pages and "Your booklets" are one column of rows in place of the card grid: a picture, a title drawn as a link, a blurb of two lines at most and the status line.
- **The submit build is 0.3.1** (`docs/hosting.md`, "The submit build"; never the published file). As of 0.3.0 its body also says what the reader saw, `booklet` and `seen`, beside `recipe` and `answers`, which are unchanged; 0.3.1 rewords the French help line under Send (checked by /localize), and sends the same body.

**Known, and left as it is in this version:**

- Printing an activity with tabs or `***` sections prints only the tab and the section on show.
- A query view or a Booklet line inside a callout other than a group in an activity (a note, a tip, any other kind, or a group in a module's or the booklet's opening) is not yet supported (sections 6 and 13): the reference renderer draws it as code or text, and the linter warns.
- A renderer served at `/app` with no slash reads its default folder at `/modules/`, by ordinary address rules; serve it at `/app/` or `/app/booklet.html` (README, `docs/hosting.md`).
- A page that drops a `booklet-store` tag it used to carry: the entries its readers opened from that store are not read from the default folder, and following the link opens the folder's file as a new entry beside the old one, which keeps its answers.
- "Read the newer file" with no host script shows no answers under a module id the newer file removed or renamed, for a declared store as for the default folder.

The marker is `booklet: "0.15"`. A file marked `"0.13"` opens with a notice; change its marker to `"0.15"`.

## Changes in v0.13.1: wording and the reference renderer

Nothing a file may say has changed: the marker stays `booklet: "0.13"`, and no file needs touching. One rule is reworded (section 12), for a renderer made of parts. The reference renderer reads a booklet the way a second reader would, and what a reader of it can notice is this.

- **Opening a file may ask for the renderer's own parts** (section 12). A conforming reader's promise was that opening a file asks the network for nothing; it is now that it asks for nothing but the renderer's own parts, from where the renderer came, and only when a booklet needs one. The reference renderer's diagram library is such a part, `parts/mermaid.js` beside `booklet.html`: a booklet with a diagram asks for it once while it is open, and a booklet with none asks for nothing. Over http or https the browser checks the part against the sha256 this renderer carries for it. Where the part cannot be had, or is not that file, a diagram shows its source under a note that says so, and the part is asked for again the next time a booklet is opened. A build can still put every part inside one file.
- **The interface language follows section 9.** The reader's own choice holds in every booklet; with none, the booklet's `lang` where the renderer has its words; otherwise English. The EN / ES / FR toggle shows in every booklet (before, a booklet's own language held the page and the toggle was hidden), and "Your booklets" is in English for a reader who never chose (before, it took the last booklet's language). A reader who chose Spanish reads a booklet whose `lang` is `es-AR` in `es-AR`, and other booklets in neutral Spanish.
- **A footnote one bare activity defines is found from another** (section 4: the activities outside every module are one module with no name). Before, the other activity drew "No citation called …".
- **What a booklet shows is kept per booklet, for the visit.** A booklet opened again keeps its pages, steps and sections. Reading a newer file over it, Clear everything, or a store booklet drawn from a file that changed since it was last read, starts them afresh (before, they were kept by place across every booklet, a newer file included). Two booklets started here no longer share their one-at-a-time and folding choice.
- **A kept entry records only what was answered**: no empty list for a lines question or a widget left untouched.
- **A booklet an earlier release kept is read by this release's rules when it opens.** If they accept it, it shows the notices a file opened afresh would show, once. If they refuse it, it opens from the design that release kept, and its notice shows on every open until the file is fixed. Before, it opened silently as kept.
- **A record kept as written for a module the booklet lacked joins the reader's work as soon as that module is added** (section 8), so the file written changes then, not at the next download and reopen.
- **Remove a module and an update of one find the module's fence outside code fences**, as Add a module always did. Before, a module line shown in a code block (a guide that shows how a module is written) could be taken for the module itself, and the lines removed or replaced were the example's.
- **A page of several is named in the pages menu by its first heading outside code fences**, the heading its links find, and an opening's leading heading that repeats the title above it is found by the same rule. Before, a line in a code block that looked like a heading (`# a comment` in a script) could name the page.
- **Citations are numbered in reading order around a question's own hint and solution.** A question's folded hint and solution are drawn inside it, so their marks are numbered before an unfolded hint written between them, which is drawn after the question: a hint `[^a]`, an unfolded hint `[^b]` and a solution `[^c]` are numbered 1 and 2 inside the question and 3 below it, the endnotes A, C, B (before, 1 and 3 inside and 2 below). Likewise, a question that is not drawn (its `menu:` names no menu) leaves its own hint and solution where it stood, ahead of an unfolded hint written before the solution.
- **In a row with no headings, a question whose id ends in `-hint` or `-solution` has a cell of its own**, as any question does. Before, it was taken for a hint and put in the cell before it.
- **Leaving the page warns unless the host says the work is saved** (with a host, `docs/hosting.md`): while a save is on its way ("Saving…"), before the host's first answer, after a failure, and now also when nothing listens through `onChange` (before, a host whose last answer was "Saved" counted even with nothing listening). The rule's three answers are `saved`, `saving` (the latest change not yet answered) and `unsaved` (no host, nothing listening, or a failed save): leaving warns unless `saved`, and the bar's save status (below) is read from it.
- **One save status, in the bar of every booklet: Saved, Saving… or Unsaved.** It is a word and a shape as well as a colour, the theme's own tones (a circled check on `good`, a dashed circle on `warn`, a warning triangle on `bad`), so it reads without colour and in forced colours. Pressed, it opens a line saying where the work is kept and why: "Saves go to: *label* · Saved 10:42", "Not saved: *message*", "Kept in this browser only". A screen reader hears it when it becomes Saved or Unsaved, not on each Saving. It is not printed.
  - With a host and one of its booklets: Saving… from a change until the host says `saved` for the latest change, then Saved; Unsaved when the answer failed, none came within 20 seconds, or nothing listens. A failure stays Unsaved, while the reader's changes go on being sent ("trying again"), until a save succeeds, so a host that keeps failing shows a steady red. A `saved` for an older change, or one that comes while a newer change is still waiting to be sent, leaves it at Saving. A change the host is never sent is never Saved: one typed while the offer to read a newer file waits, removing the last module, Clear everything (which empties this browser's copy only; the work comes back at the next open).
  - With no host (and for a booklet that is not the host's): Saved when nothing has changed since the booklet's file was read or a copy was downloaded, Unsaved after a change. Never Saving.
  - It replaces the Download button's mark and the "changes not yet downloaded" note on a booklet's home and under Finalize: one signal, not three. A booklet's card on "Your booklets" still says what it holds that is not yet downloaded.
  - Leaving the page warns as before: with a change not yet downloaded, unless the status is Saved.
- **A hosted booklet saves every few seconds, as cloud editors do** (`docs/hosting.md`). A change goes to the host once typing pauses for 2 seconds, and at most 5 seconds after the first change not yet sent while typing goes on, never on every key, and only the latest text: twelve seconds of steady typing are three saves, not one per keystroke (before, about one every half second, so a 3.4 MB booklet was sent whole about twice a second while the reader typed). It goes at once when the page is hidden or left, when the reader downloads a copy, opens another booklet or goes home, and after "Read the newer file" (the merged booklet; nothing goes before the read, so a store that keeps its own body does not offer the file straight back). A change not confirmed when the page went is sent again when it comes back from the browser's page cache. What the host is given, and the change numbers, are as before. Keeping the work in the browser is unchanged: it is written within half a second of a change, whatever the host's pace, and a change the host never answered before the page closed is sent when the booklet is next opened.
- **The renderer keeps its library in IndexedDB.** Everything it keeps in a browser (the list of booklets, each booklet's kept copy and base, the reader's preferences) is in one IndexedDB database of the site's, which holds what the browser allows a site (on a computer, hundreds of megabytes); local storage, used until now, holds about 5 MB. A large booklet, whose first keystroke used to fill local storage and switch saving off for the rest of the visit, is now kept, and found whole after a reload. The page reads the store once as it opens, before its first screen.
- **Nothing kept is lost by the move.** What an earlier release kept in local storage is copied into IndexedDB on the first visit, and removed from local storage only once the browser has confirmed the copy. A booklet changed after that both in IndexedDB and by an earlier release's tab still open (or a visit that could only use local storage) keeps the later change: its entry, kept copy and base together, by when each side last saved it. A browser that refuses IndexedDB keeps everything in local storage, as before, and "Your booklets" says so in one quiet line.
- **A notice that names the cause.** When the browser's storage is full, or fails, the page says that, and no longer says the browser is in private mode or blocks site data (that notice is now only for storage that is refused). The work stays for the visit, and the next change tries again; a removal goes first, so removing a booklet can make room.
- **Two tabs.** A tab reads what another tab kept since when it comes back into view, and before it opens a booklet, so it does not open an older copy; two tabs adding or changing different booklets keep both. A booklet open in two tabs at once is still saved by whichever tab changes it next, as before. "Your booklets" in one tab shows another tab's new booklet at once while it is in view, as before.
- **Several instances on one origin.** The renderer keeps its library in an IndexedDB database with a fixed name, `booklet`, and reads local storage through `key()` and `length` to move what earlier releases kept. A page that ran several instances on one origin by wrapping the renderer's `localStorage` calls must now also wrap the name given to `indexedDB.open` and local storage's `key()` and `length`, or give each instance its own origin.
- **"Your booklets" is drawn once on a page whose browser cannot tell whether its storage is kept** (no `navigator.storage`, as on an `http:` address that is not `localhost`): it no longer shows its "may clear" line twice, and no longer shows a host's notice twice.
- **The bar's button downloads at once, and says so.** It used to be "Send or save a copy" and opened a dialog whose only choice was "Download a copy"; it is now "Download a copy" (fr « Télécharger une copie », es "Descargar una copia") and downloads the booklet's `.md` file in one click. Nothing in a file changes.
- **The renderer follows section 8 where two `entries` blocks for one activity are read.** Entries are identified by their `ts`, and for a key both blocks hold the later wins; before, the renderer kept both entries side by side, so an entry a later block repeated showed twice. A key only one of the two holds is kept. The rule applies across blocks only: entries inside one block are kept as written, so two different entries that share a `ts` in one block (a file kept by an earlier release or a host) both stay.
- **Browsers:** the renderer states the browsers it needs (those from 2023: Safari 16.4, Chrome and Edge 111, Firefox 121; README) and carries no fallbacks for older ones. A registry entry whose address cannot be parsed is now left out of the list of modules to add (before, it was listed and then failed when added). The message for a `daily` activity with no `repeat` reads "`daily` needs `repeat`" (before, "only follows"), as the linter's does.
- **Not carried over:** the design of a booklet kept before v0.3 (it opens without it, and it is lost at its first save), and the one-at-a-time and folding choices 0.13.0 kept for booklets started here, which all shared one key.

- `parent:` is added: the field that holds the `id` of the row a row sits under, so a list of rows can nest.
- Tiles with no value are drawn as pills: a status strip.
- `fields:` has one meaning everywhere: the other fields to show (a table's columns, a list row's quieter extras, a line chart's lines, a card's questions).
- A reader's theme pick replaces a booklet's colours only; its `font` and `density` still apply, and `density` now sizes the views as well as the prose.
- A renderer may let the reader sort and filter the rows of any view, with one control, saved nowhere.
- The marker is `booklet: 0.7`.
- A file marked `booklet: 0.6` is refused; change the marker to 0.7, and in a query change `title:` to `label:` and `newest:` to `limit:`.

## Changes from v0.5

- Two **chart views** are added to the `booklet query` block (section 6): `as: bars` and `as: line`, drawn from a data block's rows or from kept entries. Nothing is computed: the rows arrive finished.
- The marker is `booklet: 0.6`.
- A file marked `booklet: 0.5` is refused; change the marker to 0.6 (nothing else in a 0.5 file needs to change).

## Changes from v0.4

- A **theme block** is added (section 7): a base theme, up to six colours, a font family and a density, each a strict named value, never CSS. The renderer works out every other colour and keeps the base theme's for any pair that would fall under 4.5 to 1.
- **Rows** are added (section 3): `> [!row]` … `> [!row end]` lays cells side by side when there is room.
- **Tone names for widget colours** (section 7): `warm`, `green`, `amber`, `slate`, `teal`, drawn in the active theme's colours. Hex pairs are still read.
- The marker is `booklet: 0.5`.
- A file marked `booklet: 0.4` is refused; change the marker to 0.5 (nothing else in a 0.4 file needs to change).

## Changes from v0.3
