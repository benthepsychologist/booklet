## Current state — renderer 0.13.1, the save status and auto-save (item `v013-save-status`; merged as #57, released in v0.13.1 on 2026-10-15)

Ben, 2026-10-14: "it's saved, saving, unsaved. green, yellow and red. with the every few seconds behavior like every other cloud editor w auto save rather than on every keystroke." Before this, a hosted booklet's `onChange` came about every half second while the reader typed (the box's host then PUT the whole 3.4 MB dashboard each time), and the reader's save signals were the Download button's mark, a "not yet downloaded" note and the host's line.

- **One status in the bar of every booklet** (`saveState`, `drawSaveState`; region 12, "THE SAVE STATUS"): `#saveBtn`, a button holding a shape from the sprite and a word, `data-state` saved, saving or unsaved, on the tone of its state (`--tone-green`, `--tone-amber`, `--tone-warm` and their deep colours: the theme's good, warn and bad, whose pairs `TH_PAIRS` already tests in all four bases). Shapes: `circle-check`, `circle-dashed`, `triangle-alert`. A transparent border shows in forced colours. Pressed, it opens `#hostLine` (hidden until then; also the button's title and description). `#saveSay`, a `role="status"` region, says Saved or Unsaved when the open booklet's status becomes one of them, and is emptied on Saving; opening a booklet says nothing. Hidden on "Your booklets" and, with the bar, in print. Drawn from `markDirty`, every answer and `renderBar`, without a redraw.
- **The states.** With an active host and one of its booklets, `hostCovers` as item 7 left it: saved, saving, unsaved (failed, no answer in 20 s, or nothing listening). A failure is sticky (the coordinator's call, 2026-10-15): `hookChanged` leaves `HOST.status` "failed" through new changes, which are still sent on the cadence (the line adds "trying again" while one waits or is on its way, `ui.saveAgain`), until a `saved` for the latest change; a failed answer clears `HOOK_SEEN`, so the next change goes again even with the same text; a change with nobody listening is a failed save (`hookFire`), so a listener that comes back never finds an unsent change counted as saved; no answer in 20 s fails a resend too; its "saving" with nothing sent or waiting (a booklet with no module, or while a link's offer waits) reads as below. Otherwise, from `dirty` and `unsavedEntries` (cleared only by a download and by reading a file): saved, or unsaved after a change; never saving. Leaving the page warns as before (a change and not saved).
- **The cadence** (`hookChanged(how)`, `hookFire`, `HOOK_IDLE_MS` 2000, `HOOK_MAX_MS` 5000, `HOOK_DUE`): a typed change (`markDirty`, a kept entry) restarts the 2 s pause within the 5 s bound; an open (a booklet opened, a host registered or allowed) is sent at once, on a 0 ms timer, after the host's script has registered; a change made without typing (a file read in) goes with one already waiting, else after the pause. `HOOK_EVERY_MS` and `HOOK_LAST` are gone. `saveLocal` no longer asks for a send: the places that change the work do, so writing the kept copy (a download's, an answer's base) never starts one. Status Saving is set at the change, so the wait counts.
- **At once** (`hookFlush`): the page hidden or left (as before), `download`, opening another booklet (`openBooklet`, `openAsView`, as before), `homeButton` (new: from an activity to the booklet's home, and to "Your booklets", where `closeBooklet` already flushed), and `hostAccept` after a newer file is read (new: the merged booklet; the cold review's S2 found that a flush before the read sent the old body, which the box's server kept and offered straight back). While a link's offer waits (`LINK_NEWER`) nothing is sent, as before. Back from the page cache (`pageshow`, `persisted`), a change not confirmed is sent again (N9).
- **A change not yet sent** (`HOOK_UNSENT`, the cold review's S1 and S3): every `hookChanged` sets it first, and only `hookFire` clears it, when it sends or finds the text is what it last sent (or a booklet with no module that nothing changed since its file was read). While it is set, `hostCovers` does not say saved, `saveState` says Unsaved when no send waits or is on its way, `hostSet` takes a `saved` as about an earlier change (Saving, or a failure left in place) and `calm` never restores "saved". So a change typed under a link's offer, made while nobody listens, the last module removed, or Clear everything (which sets it, and tells no host) is never Saved. A `saved()` naming no change counts only when the latest change sent was the open booklet's. A listener registering redraws the status. The live region stays quiet from an open until the reader acts (N1); "trying again" is not said while nobody listens (N2).
- **Answers** (`hostSet`): a `saved` (named or not) while a newer change waits to be sent leaves the status at Saving, with `HOST.prev` "saved" for when that change turns out to be no change (`calm`); a `failed` shows at once. The redraw on a failure (for the note) is gone.
- **Nothing lost by waiting.** Already true through store booklets (#52): the kept copy is written 400 ms after a change and on page hide, and the next open of the booklet draws the kept copy (its work is not in the store's file) and tells the host at once. Now tested (Node and Chromium), with a page that closes in the wait and with one that dies without `pagehide`.
- **Removed:** `markAttention`, `unsavedNote`, the note on a booklet's home and under Finalize, `.bar .navb.attention`, `.bar .hostline.bad`. Kept, since the card pills on "Your booklets" use them: `unsavedSpan`, `.unsaved`, `ui.unsavedEntries`, `ui.unsavedChanges`.

## Current state — renderer 0.13.1, storage (item `v013-renderer-storage`; merged as #54, released in v0.13.1 on 2026-10-15)

The renderer's library moves from local storage to IndexedDB, so a booklet of any realistic size can be kept. The box's 3.4 MB dashboard made a kept copy of about 6.8 million characters at its first keystroke (on 0.13.0, which the box serves), more than local storage's cap of about 5.2 million characters for a whole site (Chromium, measured); one `QuotaExceeded` then switched saving off for the visit, and the notice blamed private mode. The format is unchanged; `CHANGES.md` lists what a reader notices (under v0.13.1).

- **One database, read once, written behind** (region 3, "where the page keeps things"). `lsGet` / `lsSet` / `lsDel` keep their shape; behind them, `keepStart` opens the IndexedDB database `booklet` (object stores `kv` and `stamp`), reads all of it into memory (`KEEP.cache`) and only then draws the first screen (`bootPage`; `render` draws nothing before). A write changes memory at once and queues the key (`keepPut`); the queue goes as one all-or-nothing transaction at a time, the newest value of each key (`keepFlush`, `keepTx`), and a failed one goes back in the queue unless a newer change for its key is waiting (`keepDone`); changes made while it was on its way go at once, the failed ones with the next change. A lost connection (closed for a newer version, or Safari's "connection to Indexed Database server lost") is opened again (`keepReopen`). A file dropped before the store is read waits for it (`loadText`, like `Booklet.open`). In headless Chromium on the box the first screen comes about 60 to 120 ms later than 0.13.0's (empty store and a 10 MB one alike).
- **The list as records.** `booklet.library.v1` is kept as a head (the rest of the list and the order of its ids) and one record per entry, `booklet.library.v1#<id>` (`libJoin`, `libWrite`); `lsGet(LIB_KEY)` still returns the whole list as text. A tab writes only the entries it changed, so two tabs adding or changing different booklets keep both. Each key's stamp (which tab wrote it, a count) lets a tab re-read only what another tab wrote (`keepRefresh`): when it comes back into view or focus, and before Open and Rename from the list and before a link's booklet is decided (`keepFresh`). A change of this tab's that is waiting only because its write failed loses to a write another tab landed since, as a failed local storage write simply stopped.
- **The list's change count** (its own commit): after a landed write that touched the list (its head or a record), local storage's `booklet.tick` is set to this page's id and a count of its own (so two tabs never write the same value, which would tell no one); a tab that is in view showing "Your booklets" hears of it through the `storage` event and reads again only the list's head and entries (`keepRefresh(true)`, a re-read of its own that no open waits on), never another tab's kept copies; anything else waits for focus or view. The move's key pattern does not take it. Tested in Node (raised only by list writes, a new value each time, never moved) and in Chromium with two windows (the other's visible list shows a new booklet with no focus change; while one window saves a 4 MB booklet five times, the watching window reads none of its kept copy: 6 reads on `1a5d792`).
- **Moving from local storage** (`keepAdopt`, `keepLeft`). On every start, every key of the renderer's in local storage (`KEPT_KEY`: the list, kept copies, bases, `booklet.ui.*`, the reader's yes; and any key an older list names as an entry's `key`; another `booklet.` key stays where it is) is weighed against the store, even when local storage is too full to take a write (a read probe, `lsRead`, gates the move). The store keeps, for every key ever copied, the fingerprint of the text copied, and one per list entry (`booklet.moved.v1`, never dropped), so each start knows whether local storage changed since the copy (an older release's tab still open, or a visit that fell back to local storage, wrote it) and whether the store did. Newer wins, a booklet at a time (entry, kept copy and base together): unchanged in local storage, it is only removed; changed there only, or never copied, it is copied; changed on both sides, the side whose entry has the later `updatedAt` wins (every release sets it on each save, `noteSaved`; checked in 0.12.0 and 0.13.0), and on a tie the store. A booklet the store no longer has comes back if local storage changed it since, with that change; but an entry alone, with no kept copy on either side and no store behind it (an older tab's entry for a booklet removed here), is not listed again (it would open empty). A kept copy and its base are one side's pair: when local storage wins with a copy, its copy and its base (or none) replace the store's; with no copy there (a pointer an older tab wrote after the move), the store's copy stays with the store's own base (a kept copy is never removed for want of one, and its base is what a later read of the newer file merges against), and local storage's base is never put beside it; with no copy on either side, the store keeps no base. Never two entries for one booklet. A preference changed on both sides keeps the store's. The local storage keys are removed only when every change up to the move has landed in a strict-durability transaction, a read of the store finds them, and local storage still holds what was weighed. (The first version copied local storage over the store whenever it differed from the copy, so an older release's tab could bring back an answer this release had written over since: the cold review of `c3d19a0` reproduced it with the real 0.13.0 in a second tab.)
- **Mirrored keys**: `booklet.ui.theme` (the head script paints it before the store can be read; the theme menu now also writes it to the store) and `booklet.host.allowed` (`Booklet.host`, called by a host's script right after the main script, decides on it). A mirror the store lacks is moved in. The theme: every renderer writes its mirror, so a mirror that differs from the store holds the latest pick and the store takes it, unless local storage takes no write (its mirror is stale then: the store's is painted). The reader's yes is kept only where the store and its mirror agree; where they differ (a Stop, or another label allowed, in a visit that could write only local storage) it is forgotten and the host asks again. A host registered early is decided again (`HOST.early`).
- **Without IndexedDB** (open throws or fails, takes over 5 s, or its first whole read takes over 15 s; a read that ends after that is not loaded): mode `ls`, local storage exactly as before. "Your booklets" says so before anything else, so an empty list after the move is explained: a refusal as a quiet line (`storageSmall`: booklets kept in the larger store are not shown), a timeout as a notice (`storageLate`: they could not be read this time, and a reload brings them back; Safari's first-open hang is the real case). With no IndexedDB at all (Node, where the tests run) it is `ls` silently, so every Node test runs the old path unchanged.
- **Notices name the cause** (`keepNotice`): `storageOff` only for storage refused at start (as before; local storage that is full at start is `storageFull` when IndexedDB is not used, and nothing once it is), `storageFull` for a quota error (IndexedDB's own, or local storage's in mode `ls`, which says the small store is full), `storageFailed` for any other write error. Told once as a toast and on "Your booklets" while it lasts; the next change tries again, removals first when the store is full; a write that lands ends it. A lost connection is opened again, and if that was tried less than five seconds before, by itself when they are up.
- **Leaving the page** (its own commit, for item 7 to meet): `pagehide` and a hidden page also call `keepFlush(true)`, which starts a transaction even while one is on its way, carrying that one's changes too (so a base never lands without its copy), and calls `commit()`.
- **Clear everything** removes the open booklet's kept copy and base from the store and any local storage leftover of them (`lsDel` takes the key out of both), as it cleared them from local storage before.
- **Strings:** `ui.storageFull`, `ui.storageFailed`, `library.storageSmall` and `library.storageLate` are new (`storageSmall` reworded in the fix round to say what it hides); their fr, es and es-AR are checked by /localize (2026-10-14: es `storageFull` no longer reads as a command, "Your booklets" is quoted as the screen's name), no draft mark is left, and `callouts.test.js` is main's strict check again. Questions the checks raised about the English go to Ben; the English is unchanged.

## Store booklets open from the store (renderer, 2026-10-13/14; merged as #52, released in v0.13.0 on 2026-10-14)

For a store booklet (`from: store:<name>`) the store's file is the truth, and what the browser keeps of it is only a buffer for work the store may not have yet. `CHANGES.md` lists what a host or a reader will notice (under "Changes from v0.12").

- **Listed at once, as a pointer.** It joins "Your booklets" as soon as it is read, with no kept copy of its content (`notePointer`), on a page that declares a store. A kept copy (`booklet.b.<id>`) appears only once the reader changes something.
- **A base for each kept copy** (fourth round): beside `booklet.b.<id>`, `booklet.base.<id>` holds the records (answers, entries, drafts; never the body) of the file text the copy is based on: the file it last drew or read, or the text the host last confirmed with `saved(change)` for the latest change sent for that booklet (`hostAnswered`, which works for a booklet no longer open). For the 3.4 MB dashboard it is the size of the reader's records: 92 characters for one answer of a sentence, against 6.8 million for the kept copy.
- **Drawn from the store** (`storeHolds`): opening it again, by its link or from the list, reads the file and draws it, into the same entry, and drops the kept copy, when the kept copy has no change to the booklet itself (`customized`) and either nothing changed here since the base (the file is drawn whatever it holds: another device's work just appears) or the kept copy and the file hold exactly the same work (`flatWork`, an empty value counting as none). A kept copy with no base takes that second test alone; a blank one is judged one way only (`workWithin`). Otherwise the kept copy opens, with the offer if the file changed. It is decided on content when the booklet opens, whatever the host has done.
- **One rule for reading a newer file**, whether a link found it (`linkAccept`) or the host pushed it (`hostAccept`, `fileChanged`): the new file's body, and with a host the records merged place by place against the base (`acceptWork`, `mergeWork`): changed here only, here's; changed there only, the file's; changed on both, here's, except that a removal here (an answer cleared, an entry deleted, a draft emptied) loses to a change there, the one removal rule everywhere (final check); a removal the file did not touch stays removed, so a draft emptied by a finalize leaves no duplicate. A kept copy with no base is merged once the older way (`withFileWork`: what holds something here wins). With no host, the reader's own records stay as they are. The host then saves the result, and the file's records are the new base.
- **Moves read from the new body** (`followMoves`, final check): the rule of the box's `storefile._retarget`, ported, so the browser and the store agree on every move. Work under a scope the new body has no module for, whose id is an activity of the new body (not a bare one), goes to the one scope that activity and every activity the work names now share; a module that still exists keeps its work, and work whose activities now sit in different modules stays as written. Because it reads the body, not the records, it also follows a first answer that was unsent when the generator moved its module (M8). Checked against the real `storefile.write_generated` for a partial move (followed on both sides) and a split one (left on both). Short check: the activities the work names are counted from the base alone (the records the store decided from), so an entry only this browser holds no longer makes it refuse the store's move (p20); a module line with no id is skipped, as storefile does; and work left under a scope no module owns (a refused move, a removed module) is written back as records kept as written under its old records line (`keepUnowned`, format 0.13's kept-as-written path), so it survives as the store's own such records do (p21).
- **The base is never ahead of the kept copy** (final check): when the host confirms the open booklet's latest change, the pending kept copy is written first (`flushSave` in `hostAnswered`), so a crash right after a fast host's answer cannot leave a copy older than its base.
- **What the base cannot do:** a host that names no change never moves the base, so its saved work counts as changed here until the next file read (more offers, and a conflict keeps the browser's value); two tabs saving one booklet share one kept copy and one base, so the last write wins, as before. An upsert-by-day activity edited on two devices on the same day keeps both entries (nothing is lost, but its one-a-day view then shows two).
- **A change in the last half second before the tab closes is sent** (`pagehide` and a hidden page run `hookFlush` as well as `flushSave`). For a large booklet that save may not arrive before the page goes, and nothing is lost when it does not: the kept copy holds the work, and the next open shows it with the offer.
- **The first version (36d7126) was refused at its cold review.** It used a `hosted` flag set by the host's `saved()`. That flag is gone, and so is its clause letting older entries through on their flags.
- **Rename in the list** gives a store booklet a name of its own there (`named`) and writes nothing into what is kept (the first version wrote a blank booklet into a pointer, which a late host then saved over the file's records).
- **Never sent blank.** A booklet with no module is never sent to the host (`hookFire`), and a change still waiting its half second is told to the host as its booklet is left (`hookFlush`), not in the next booklet's place.
- **The host's answer may name its change.** `onChange` gives `change`, a number; `saved(change)` / `failed(message, change)` about an earlier change or another booklet leave the bar as it is. Without it, as before (docs/hosting.md).

Open from the list falls back to the kept copy only when its own read failed, not when a newer one superseded it. Removing an entry while its file is read drops that read. `openLinked` writes a pending save before it decides. Download makes no kept copy for a pointer.

- **Citations** are CommonMark footnotes, drawn as numbered marks with a side
  panel.
- **Records** sit in a `%%`-wrapped section at the end of the file.
- **Interface languages:** English, French, Spanish and Argentine Spanish.
- **Four themes the reader picks** (renderer 0.4.1, no format change): Paper, Daylight, Night and Contrast,
  chosen from a menu in the top bar; Auto (the default) follows the device live. The choice is kept in the browser
  only, never in a booklet. A booklet may ask for a look of its own (a `booklet theme` block, renderer 0.5.0): Auto then means the booklet's look, any explicit pick wins, and the look applies only while that booklet is open. Every colour in the renderer's CSS is a token in
  the four tables (`test/themes.test.js` checks the tables match, WCAG contrast, and that no colour literal is left;
  `test/themes-browser.js` checks the switching in Chromium). Diagrams are re-drawn in the active theme; print is
  always light.
- **Theme block, rows, tone names** (format 0.5, renderer 0.5.0). The theme block is validated key by key and
  applied as computed `#rrggbb` tokens (no text of it ever reaches a style); a colour pair under 4.5 to 1 is dropped
  for the base theme's own, and the linter warns which. Rows are a CSS grid of cells (one column under about 45rem).
  Widget colours are tone names drawn in the theme's tone tokens. Checks: `test/theme-block.test.js`,
  `test/theme-block-browser.js`.
- **The page is wide.** The 64-character column is gone: the content area runs to about 76rem, prose (paragraphs,
  lists, callouts, questions, folded reading cards) stays at about 70 characters, and query views, widgets and
  figures use the width. Tiles fill the row, a grouped list lays its groups out as cards side by side when there is
  room, and everything is one column on a phone.
- **Diagrams and math are drawn.** A ```` ```mermaid ```` fence is drawn as SVG
  where `![[#^id]]` embeds it, or in place when it sits in the prose; `$…$` and
  `$$…$$` are typeset as MathML. A diagram that will not parse shows its source
  with a one-line note, and a formula Temml cannot read shows as its TeX. Both
  libraries (mermaid tiny 12.1.0, Temml 0.13.5, MIT, listed in `NOTICE`) are
  stored inside `booklet.html` as inert text and run only when a booklet has a
  diagram or a formula, so a booklet with neither never runs them; the file
  still opens straight off disk and under the hosted site's Content-Security-Policy
  (no `unsafe-eval`, no network). The file is about 3 MB because of them.
  `test/figures.test.js` checks the stored copies and when they wake;
  `test/figures-browser.js` draws real examples in Chromium under that policy.
- **Plain Markdown reads as a booklet.** A file with booklet front matter and no
  activity line is one activity named by its title (`SPEC.md` section 3), with or
  without questions. `<!-- … -->` comments are not drawn but are kept in the saved
  file, and prose tables are styled (scrolling inside their own wrapper).
- **Reading-only activities open folded.** An activity with no question, widget or
  query, and at least two sections on a page, draws each section as a disclosure
  showing its heading and first paragraph, with "Open everything" / "Fold everything",
  an "Opened N of M sections" line, section entries and dots in the pages menu, and
  heading links that open the section they target. The reader's choice is kept per
  booklet in the browser, never in the file. An activity with any question draws as
  before. The registry's `what-is-a-booklet` module now folds.
- **Charts** (format 0.6, renderer 0.6.0). `as: bars` is one list row per data row (label, a decorative bar from zero, the value at its end), `as: line` an SVG redrawn to its container's width with one line per field (distinct colour, dash and marker), gaps for non-numbers, thinned x labels and a legend. Checks: `test/charts.test.js`, `test/charts-browser.js`.
- **Row roles and the sort-and-filter control** (format 0.7, renderer 0.7.0). One resolver (`rolesOf`) decides which field plays each role, once per query, and every view receives resolved roles and never reads the raw query. One pipeline (`viewNodes`) owns the default view, the empty text, `limit`, filter, sort and grouping; the control (`viewControls`) is drawn once above a query's rows when there are 9 or more, and its state lives in a module-level map that is cleared when another booklet opens. `list` draws one line per row; A list whose rows carry `parent` is drawn nested with native `details`/`summary` (`nestRows` builds the tree in one pass; every row starts closed; what the reader opens is kept in the query's view state beside the sort and filter, never saved; a filter keeps matches with their ancestors and opens them while it is on). A page whose name is its own first heading is no longer named twice, and grouped-list cards are at most two across. The "Show the numbers" table under a chart is no longer sortable on its own, so that sorting it cannot redraw the chart. Interface strings for the control are written in all four languages and have not yet had a person's review (see the `localize` skill).
- **The spec, the linter and the renderer agree** (format 0.8, renderer 0.8.0). The settings table is one constant, `KIND_SETTINGS`, in the renderer, the linter and `SPEC.md`, pinned together by `test/guard.test.js`. A problem a file's reading finds carries a severity: the ones `SPEC.md` section 12 says a reader refuses (a module opened and not closed, closed and not opened or overlapping, an id used twice, a reference across a module boundary) stop the file opening and show their messages in the load dialog; every other one is counted in a notice at the top of the booklet's first screen, with the list in a disclosure, dismissible for the session. A reader's own options (`open`) and `[x]` marks are drawn by `drawChoice`; a `multi`'s Check marks live only in the page, never in the file. The per-value language machinery (`pickLoc`, `locBag` and the rest) is gone: a file has one language and its values are plain strings. A widget's `copy` saved in the browser by an earlier version is read as written, so a booklet saved under 0.7 shows no widget words until its file is loaded again.
- **An id belongs to its module** (format 0.9, renderer 0.9.0). The parser keeps its claims per module (one table for module ids, one for the data section), reads a records line's module id to know whose the record blocks are, and gives each activity an address, `module-id/activity-id` (`scopeOfAddr`, `addrOf`, `shortId`; just the id for an activity outside every fence). The address is the key of `STATE.entries`, `DRAFTS.custom`, the screen on show, `go`, `activityOf`, `holderOf`, the page position, the reading-mode state, the per-view state and a query's `from`. Once-answered questions are kept in one map by scope, `STATE.answers[scope][questionId]`, where scope is a module's id or `""` for the activities outside every fence (`answersIn`, `peekAnswers`). A widget block carries its module (`widget.module`), a figure is kept under `module-id/figure-id` (`figureFor`), a menu is found in its own module and then the data section, a footnote registry falls back to the data section's (the linter warns when one footnote id is defined twice in a module). Add a module no longer refuses an id another module uses; it refuses only a block the module brings into the data section under an id that section already has. **Rename on a clash** (`renameClashingIds`, one block in the Add a module part of the main script, and one call in `addModuleText`): a block id or footnote id the incoming module shares with another module or the data section is written into its text as `<module-id>-<id>` (`-2`, `-3` if taken), with its `^id` line, embeds and links, a query's `from:` and a footnote's marks and definition following; code fences and inline code are left alone; question, activity, widget-line and menu ids are never renamed; an update renames the same way. The linter warns when two modules share a block id or a footnote id (Obsidian and GitHub read those across the file). **Add a module** adds every module a file holds (each one's lines, in file order, through the same check and rename), puts the blocks outside every fence into the data section once, replaces a module already there where it sits (the order never changes), writes a `title` when it starts a booklet's front matter, and reads the design back from the file it wrote, so the screen shows what the file holds. A heading link (`[[#Heading]]`, `](#slug)`) is looked for in its own module only (`linkHooks`); the linter warns for one whose heading only another module has. A message shown to a reader has its backticks turned into quotation marks (`humanMsg`). Checks: `test/modulescope.test.js`, `test/modulescope-browser.js`, `test/addmodule.test.js`.
- **A module's notice, its own data section, and a booklet's name** (format 0.10, renderer 0.10.0). The parser reads a `notice` callout into the module (`notice` is a kind in `KIND_SETTINGS`, with no settings) and a data line's module id into a scope the lookups already knew (`scopeMod` in `readBlocks`); `addModuleText` sorts what a file holds outside its fences by module, writes a notice only found in front matter as a callout, and replaces a module's fence and its `> [!data|module-id]` section together; `setTitleIn`, `nameBooklet`, `renameBooklet` and `renameStored` rewrite the one `title:` line, and a booklet started in the browser gets its front matter from `blankBook`. `test/version.test.js`, `test/notice.test.js`, `test/datasection.test.js` and `test/bookletname.test.js`, and `test/notice-browser.js`, pin them.
- **Another marker opens, no image is fetched, a small booklet opens into itself** (format 0.11, renderer 0.11.0; 0.11.1 adds open by link). See "Current state" above.
- **The linter** checks v0.11 files by v0.11's rules (another `0.x` marker is a warning) and agrees with the
  renderer about what is wrong.
