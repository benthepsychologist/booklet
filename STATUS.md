## Current state — renderer 0.13.1, structure (item `v013-renderer-structure`; merged as #51, not yet released)

The renderer reads a booklet the way a second reader or a build step would (review D16, R1 to R3) and speaks the interface language SPEC section 9 gives it (D17, R4). The format is unchanged.

- **R1, the design is its text's parse.** A snapshot keeps `{S, D, text, dirty, unsavedEntries}`: `text` is the booklet's text with nothing of the reader's in it (`bookText`), parsed again on every open (`adoptText`). Add a module, Remove a module and Rename compose the text and adopt its parse whole; `bookOk`, `moduleOk`, `kindOk`, `adoptBook`, `addWidget`, `addModule`, `editBook`, `nameBooklet`, `blankBook` and the two merges are gone, and `customized` is no longer the design's: it is the snapshot's (`CUSTOMIZED`, set by Add, Remove and Rename and cleared by a file read), which a store booklet's open reads. An older snapshot (the parsed design, `TPL`) opens from `TPL.raw.source` with the records it kept as written. A booklet started here takes its title's slug as its id. `toMarkdown` is `fileText(BOOK, STATE, DRAFTS)`.
- **R2, a pure parse.** `parseBooklet(text, {icons})` is handed the icon names, read once from the sprite (`ICON_NAMES`); `plainText` reads inline Markdown as text with no page (the inline reader takes its element maker from its context). A problem is `{code, args, refuses}` (`PROBLEM.<code>(...)`), worded by `problemText` only where it is shown, so a file's notices follow a language switch.
- **R3, one drawing context.** A view holds a record per activity address (it replaces `openChip`, `VIEWSTATE`, `WK`, `SOL_SHUT`, `PAGE_NOW`, `OAT_AT`, `RM_STATE`); `VIEWS` keeps one per library entry for the visit, `VIEW` is the open booklet's, and `viewReset(id, what)` is the one place a view is chosen or cleared (an opening keeps the page, steps, sections and shut solutions and starts the open entry, query sorts and wiki menu afresh, as before). `render()` makes a draw context (ticks, reading plan, heading to reveal, citation scopes, opening) passed to every screen and block, in place of `RM_CUR`, `LINK_AT`, `RM_REVEAL`, `RM_REVEALED`, `CITE_OPENING`, `CITE_GEN`, `ANSWER_TICKS` and `SCOPES`. `settle()` decides the language, the screen and a daily activity's draft before a draw; drawing writes no state. The one-at-a-time and folding preferences are kept under the library entry (its link for a booklet opened by one).
- **R4 (D17), the interface language.** The reader's chosen language, whatever a booklet says; else the booklet's `lang` where the renderer has its strings; else English. The EN / ES / FR toggle always shows. `languages`, the offer and variant logic, and the language a snapshot or entry carried are gone.
- **On the store-links fix (#52; rebased onto v0.13.0).** Every store-links behaviour and test holds, through the new forms. `storeHolds` reads the kept design from the snapshot's text (parsed) or an older release's `TPL`, and `customized` from the snapshot. The work `keepUnowned` writes back as records kept as written is adopted through the design's text (`finishLoad`), so the design stays its text's parse. A store booklet drawn again from the store keeps its view when the file is the one it last read (`storeSeen`) and starts it afresh when the file changed. `notePointer` records no `lang` (R4). `openAsView(text, via, {page, reuse, parsed})`, `openLinked(text, via, {entry, page})` and `finishLoad(R, {via, keep, page, view})` each take one options object, and `LINK_AT` is gone (the page is passed down).
- **What a reader can notice** (`CHANGES.md`, under v0.13.1): the toggle in every booklet, and the reader's choice followed in it (before, a booklet's own language held the page and the toggle was hidden); "Your booklets" in English for a reader who never chose (before, the last booklet's language); a choice of Spanish reads a booklet whose `lang` is `es-AR` in its own `es-AR`, and other booklets in neutral Spanish; two booklets started here no longer share their one-at-a-time and folding choice; a footnote one bare activity defines is found from another (SPEC section 4; before, "No citation called ..."); reading a newer file over a booklet, or clearing everything, starts its pages, steps and sections afresh (before, only the open entry and the query sorts were); a store booklet drawn again from its store keeps its pages, steps and sections when the file is the one it last read and starts them afresh when the file changed (before, it kept them either way); a kept entry no longer records an empty list for a lines question or a widget left untouched; a booklet an earlier release kept is read by this release's rules when it opens: if they accept it, it shows the notices a file opened afresh would, once, and its snapshot is rewritten as text there and then, with no save (the host is told nothing and its last-updated time stays); if they refuse it, it opens from the design that release kept, saved back so, and its notice shows on every open until the reader fixes the file (before, it opened silently as kept); a record kept as written for a module the booklet lacked joins the reader's work as soon as that module is added (SPEC section 8), so the file it writes changes then rather than at the next download and reopen; a snapshot from before v0.3 (no `raw.source`) opens without its design, which is lost at its first save; the one-at-a-time and folding choices 0.13.0 kept for booklets started here, all under the shared key `local/booklet`, are not carried over.

## Store booklets open from the store (renderer, 2026-10-13/14; merged as #52, released in v0.13.0 on 2026-10-14)

For a store booklet (`from: store:<name>`) the store's file is the truth, and what the browser keeps of it is only a buffer for work the store may not have yet. `CHANGES.md` lists what a host or a reader will notice (under "Changes from v0.12").

- **Listed at once, as a pointer.** It joins "Your booklets" as soon as it is read, with no kept copy of its content (`notePointer`), on a page that declares a store. A kept copy (`booklet.b.<id>`) appears only once the reader changes something.
- **A base for each kept copy** (fourth round): beside `booklet.b.<id>`, `booklet.base.<id>` holds the records (answers, entries, drafts; never the body) of the file text the copy is based on: the file it last drew or read, or the text the host last confirmed with `saved(change)` for the latest change sent for that booklet (`hostAnswered`, which works for a booklet no longer open). For the 3.4 MB dashboard it is the size of the reader's records: 92 characters for one answer of a sentence, against 6.8 million for the kept copy.
- **Drawn from the store** (`storeHolds`): opening it again, by its link or from the list, reads the file and draws it, into the same entry, and drops the kept copy, when the kept copy has no change to the booklet itself (`customized`) and either nothing changed here since the base (the file is drawn whatever it holds: another device's work just appears) or the kept copy and the file hold exactly the same work (`flatWork`, an empty value counting as none). A kept copy with no base takes that second test alone; a blank one is judged one way only (`workWithin`). Otherwise the kept copy opens, with the offer if the file changed. It is decided on content when the booklet opens, whatever the host has done.
- **One rule for reading a newer file**, whether a link found it (`linkAccept`) or the host pushed it (`hostAccept`, `fileChanged`): the new file's body, and with a host the records merged place by place against the base (`acceptWork`, `mergeWork`): changed here only, here's; changed there only, the file's; changed on both, here's, except that a removal here (an answer cleared, an entry deleted, a draft emptied) loses to a change there, the one removal rule everywhere (final check); a removal the file did not touch stays removed, so a draft emptied by a finalize leaves no duplicate. A kept copy with no base is merged once the older way (`withFileWork`: what holds something here wins). With no host, the reader's own records stay as they are. The host then saves the result, and the file's records are the new base.
- **Moves read from the new body** (`followMoves`, final check): the rule of the box's `storefile._retarget`, ported, so the browser and the store agree on every move. Work under a scope the new body has no module for, whose id is an activity of the new body (not a bare one), goes to the one scope that activity and every activity the work names now share; a module that still exists keeps its work, and work whose activities now sit in different modules stays as written. Because it reads the body, not the records, it also follows a first answer that was unsent when the generator moved its module (M8). Checked against the real `storefile.write_generated` for a partial move (followed on both sides) and a split one (left on both). Short check: the activities the work names are counted from the base alone (the records the store decided from), so an entry only this browser holds no longer makes it refuse the store's move (p20); a module line with no id is skipped, as storefile does; and work left under a scope no module owns (a refused move, a removed module) is written back as records kept as written under its old records line (`keepUnowned`, format 0.13's kept-as-written path), so it survives as the store's own such records do (p21).
- **The base is never ahead of the kept copy** (final check): when the host confirms the open booklet's latest change, the pending kept copy is written first (`flushSave` in `hostAnswered`), so a crash right after a fast host's answer cannot leave a copy older than its base.
- **What the base cannot do:** a host that names no change never moves the base, so its saved work counts as changed here until the next file read (more offers, and a conflict keeps the browser's value); two tabs saving one booklet share one kept copy and one base, so the last write wins, as before. An upsert-by-day activity edited on two devices on the same day keeps both entries (nothing is lost, but its one-a-day view then shows two).
- **A change in the last half second before the tab closes is sent** (`pagehide` and a hidden page run `hookFlush` as well as `flushSave`). For a large booklet that save may not arrive before the page goes, and nothing is lost when it does not: the kept copy holds the work, and the next open shows it with the offer.
- **The first version (36d7126) was refused at its cold review.** It used a `hosted` flag set by the host's `saved()`. That flag is gone, and so is its clause letting older entries through on their flags.
- **Rename in the list** gives a store booklet a name of its own there (`named`) and writes nothing into what is kept (the first version wrote a blank booklet into a pointer, which a late host then saved over the file's records).
- **Never sent blank.** A booklet with no module is never sent to the host (`hookFire`), and a change still waiting its half second is told to the host as its booklet is left (`hookFlush`), not in the next booklet's place.
- **The host's answer may name its change.** `onChange` gives `change`, a number; `saved(change)` / `failed(message, change)` about an earlier change or another booklet leave the bar as it is. Without it, as before (docs/hosting.md).
- **"Opening <name>…"** shows on whatever screen is up while a file is read, and goes when the read ends however it ends, or a newer link takes over (`LINK_LOADING` is `{gen, label, from}`). Open from the list falls back to the kept copy only when its own read failed, not when a newer one superseded it. Removing an entry while its file is read drops that read. `openLinked` writes a pending save before it decides. Download makes no kept copy for a pointer.
