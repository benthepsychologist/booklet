# Hosting Booklet

This page is for someone who serves the renderer (`booklet.html`) on their own site or machine. It covers what the renderer reads from a host: a store of booklets, the default folder `modules/`, the images and data files beside a booklet, and the host's choice of look. **The renderer reads from a host and never writes to one.**

It describes renderer 0.20.2 and later (the section on `window.bookletStyle`, 0.12.0 and later; the default folder, `modules/` beside the renderer, 0.15 and later; the refusal to write records after a body that ends inside a code fence that never closes, 0.16 and later; the data files a store booklet names, 0.19 and later). The format (`SPEC.md`) is not involved: nothing here changes what a booklet file may say.

## A host's default look: `window.bookletStyle`

Before the renderer's own script runs, a small script in its head sets the page's look. A host can choose which of the renderer's two styles a booklet is drawn in when the booklet does not ask for one.

- `bookletStyle.names` is the two styles, `["teaching", "briefing"]`. `teaching` is soft tiles with pictures, for working through; `briefing` is solid tiles with icons, for reading at a glance. A style changes shapes and where colour goes, never the colours themselves.
- `bookletStyle.set(name)` is the host's **default**: the style drawn for a booklet whose theme block has no `style:`. A name that is not one of the two is ignored. Call it any time; the open page draws again.
- `bookletStyle.get()` is the style in force right now, whoever chose it, and `bookletStyle.picture()` is `"spot"` or `"icon"`, the kind of picture a card asks for in it.
- **A file's `style:` wins over the host's default.** A booklet whose theme block says `style: briefing` is drawn as briefing while it is open, whatever the host set, and whatever colour theme the reader picks. When the reader leaves it (back to the list of booklets), or opens one with no `style:`, the host's default holds again. `bookletStyle.set` while such a booklet is open changes the default and nothing on screen.

```js
window.bookletStyle.set("briefing");   // this site's booklets read as briefings unless a file says teaching
```

## The promise, and where the line is

Booklet's promise to readers is that nothing they write is uploaded. It runs in their browser, and their work stays there or in a file they save themselves. The renderer is a core, `booklet.html`, and its parts (today one, `parts/mermaid.js`, the diagram library), and anyone can copy and host it, so the promise has to hold for the file, not only for one site. A host serves `parts/` beside the renderer, at the renderer's own address (`/app/` and `/app/parts/mermaid.js`), as `text/javascript`; or it serves the one-file build (`node test/one-file.js`), which holds every part and needs no `parts/`. Opening a file asks the network for nothing except the renderer's own parts, from where it came, and only when a booklet needs one, with the one exception below for a page whose host declares a store or that reads its default folder: a booklet with no diagram makes no request, and one with a diagram makes one, a plain read of `parts/mermaid.js`, once while it stays open (if it cannot be had it is not asked for again until a booklet is opened again). The one exception is an image. A booklet opened from the store the page declares may have its images read from that same store, and one opened from the default folder from that folder: one plain read of the store's or folder's own address plus a checked relative path, never an address the booklet spells out ("Images" in the store contract below). A booklet from a file, from the registry, or from a default folder this page does not have makes no image request, and neither does a part of a store booklet whose text is not the store's own (a module the reader added or updated afterwards, or a kept copy of an older file or of another store's or another default folder's file). So a booklet with no diagram and no image read from a store or the default folder makes no request at all. Serve the renderer at a URL that ends in `/` or in the file name (`/app/` or `/app/booklet.html`): at `/app` with no slash the part would be looked for at `/parts/mermaid.js`. Over http or https the page gives the part's script an integrity attribute, the part's sha256 (the same digest the `<!-- PART:` notice gives in hex), so the browser itself refuses a part that is not the pinned file: a stale part from another release, a wrong file or a changed one. The diagram then shows its source under the note that its part could not be loaded, and the next open asks again. Serve the part exactly as published, byte for byte (compressing it in transit is fine; rewriting or minifying it is not). A page opened from disk cannot check an integrity attribute (Chromium refuses even the right file), so from disk the part has none and is trusted as the renderer is: the same folder, the same release. A host that wants it revalidated, not refetched, sends an `ETag` and `Cache-Control: no-cache`.

**The published `booklet.html` holds no code that sends a reader's work anywhere, and never will.** Two checks guard that, over the exact file that is published:

- `test/guard.test.js` (its static check at the end) lists the browser's ways of sending (`XMLHttpRequest`, `sendBeacon`, `WebSocket`, `postMessage`, `BroadcastChannel`, forms and the rest), requires that none appears in the hand-written code, and pins the two places the renderer makes a request: the one `fetch` (a single read, with no method, no body, no credentials, no redirect, a size cap and a timeout; an image from the store, or from the default folder, is read through it too) and the one script element that loads a part from `parts/NAME.js` beside the page. It also pins the one `img` element the renderer builds from a booklet's Markdown, which takes its address only from a `blob:` URL made from bytes that fetch read.
- `test/pledge-browser.js` runs the file in a real browser, under the hosted site's strict Content-Security-Policy and again with no header at all (the renderer's own policy, below, is then the only one), uses it (typing, keeping entries, a diagram, a formula, opening a booklet by link from a declared store and, 0.15, from the default folder, with one image beside it) and asserts that every request it made was a plain read, that the only ones beyond the page itself and the registry were the renderer's own part (`parts/mermaid.js`, once, only for a booklet with a diagram), the one booklet each link named, and the one image beside the default folder's booklet (both only after its link was followed), and that nothing the reader typed appears in any of them.

**The file also carries its own Content-Security-Policy** (0.11.6), a `<meta http-equiv="Content-Security-Policy">` tag directly after the charset tag, so the block does not depend on the host's header. It allows the page's own scripts only (the theme script, the main script and each library the file holds, each by sha256, which is Temml in the core and both libraries in the one-file build, and the page's own parts by `'self'`; no inline script of a host's, and no `unsafe-inline` or `unsafe-eval` for scripts), images only from `data:` and `blob:`, fonts only from `data:` (0.11.8: the renderer carries Atkinson Hyperlegible and Lexend inside itself, so a header you set must allow `font-src data:` or the page falls back to system fonts), and connections only to the page's own origin and `https://raw.githubusercontent.com`. It also sets `x-dns-prefetch-control: off`, because a policy does not govern the name lookups a browser may make for the hosts of links on a page. What this means for a host:

- **A script of yours is a file on the page's own origin**, added with `<script src="/your-host.js">` (to call `bookletStyle.set`, say). An inline script in your page does not run.
- **A store must be on the page's own origin** (`booklet-store` is a path on your site), and your own header must allow it in `connect-src`. The default folder (`modules/` beside the renderer, which a page with no `booklet-store` line reads `#/open/<name>` links from) is on the page's own origin by its nature, so a header you send must allow `'self'` in `connect-src` for it; one that does not (bookletmd.org's) blocks it, and the link says the booklet could not be fetched. A **registry** must be on the page's own origin or on `raw.githubusercontent.com`, and so must the module files it lists. The renderer's registry address is in its own `booklet-registry` tag, so a host that points it elsewhere is already editing the file and must edit the policy too.
- **Your header can only tighten the policy.** A second policy does not loosen the first: both apply. `frame-ancestors` cannot be set from a meta tag, so it stays in your header if you want it.
- **A host that needs anything else must edit the renderer**, which changes its checksum (see "Checking that a host serves the real renderer"). After any edit to the renderer's scripts, `node test/csp-hash.js --write booklet.html` recomputes the hashes; `node test/csp-hash.js --check booklet.html` says whether they are current, and `test/guard.test.js` fails if they are not.

A host serves the **unmodified** `booklet.html`. The renderer reads what the host serves and sends nothing back; a reader keeps their work in their browser, or in a copy they download.

## Which booklets come from the host's store

A booklet is **a store booklet** when it was opened by a `#/open/<name>` link from the store the page declares. The renderer remembers that (the booklet's entry in "Your booklets" says `store:<name>`), so it is still a store booklet when the reader opens it again from the list. The store is only read.

A booklet opened by `#/open/<name>` from **the default folder** is not a store booklet (0.15). On a page with no `booklet-store` line, served over http or https, a link reads `modules/<name>` beside the renderer, so you can serve the released file unchanged. That folder is where the page came from, not a store you declared: its entry says `modules:<folder>#<name>` (the folder's path on your site, such as `/app/modules/`, so copies of the renderer at two paths of one site never share a reader's work for the same name, and a pointer from one is not listed on the other), the bar says it is kept in this browser only, and the submit build shows no Submit for it. It draws its images from the folder by the same rule as a store's ("Images" in the store contract). A host that declares a store does so with the `booklet-store` line, which always wins over the default folder.

Every other booklet is **the reader's alone**: one picked from the reader's own disk, pasted or dropped, started new, or opened by a `#/module/<id>` link.

## What the reader sees

- **One save status, in the bar of every booklet**: **Saved** or **Unsaved**, in a word and a shape as well as a colour (a circled check on the theme's `good` tone, a warning triangle on its `bad` tone), so it reads without colour too. Pressed, it opens the line behind it, which is also its title. A screen reader hears it, politely, when it becomes Saved or Unsaved once the reader has done something in the booklet, not for the state a booklet opens in. It is not printed.
- **Saved** means nothing has changed since the booklet's file was read or a copy was downloaded; **Unsaved** means something has. The line says "Kept in this browser only" (or, while it is saved, that nothing has changed since the file was opened or downloaded). This is true of every copy of the renderer, whatever page serves it. Leaving the page (closing the tab, reloading) with work not yet downloaded asks the reader first unless the status is Saved.
- "Download a copy" gives the booklet's file text, with the reader's work in its records section. A body that ends inside a code fence that never closes would have records written after it that the next open would read as part of the fence (SPEC section 8), so Download a copy is refused, with a notice saying why in the reader's language. Nothing the reader did is cleared, the status stays Unsaved, and the fence is not closed for the author. A text with nothing to put after the body (no answers, or the answers taken back) is the file as it was, and downloads as usual.

## Where the renderer keeps a reader's work

From renderer 0.13.1, everything the renderer keeps in a reader's browser is in one IndexedDB database of the page's origin, named `booklet`: the list of booklets, each booklet's kept copy (and, for a store booklet, its base: see "The store contract"), and the reader's preferences (the theme, the language, how each booklet is shown). IndexedDB holds what the browser allows a site, which on a computer is hundreds of megabytes. Local storage, which earlier releases used, holds about 5 MB, and one large booklet's kept copy filled it, after which nothing more was kept for the visit.

- **Read once, at start, and written behind.** The renderer reads the whole store before it draws its first screen, and writes each change after it is made, in order. A change still being written when the page is hidden or left is handed to the browser then.
- **Local storage keeps a count, `booklet.tick`**, raised when a change to the list lands, so another tab showing "Your booklets" hears of it (IndexedDB tells no other tab) and reads the list again, nothing more. It holds the writing page's id and a count, nothing else.
- **The theme is also mirrored in local storage** (`booklet.ui.theme`), for a read made before the store is read, so the page is painted in the reader's theme before the first frame. The store is read a moment later.
- **What earlier releases kept in local storage is moved** into the store on the reader's first visit with 0.13.1, and removed from local storage only after the browser has confirmed the copy. A booklet that an earlier release's tab, still open, changes after that is weighed at the next start against what the store holds: the later change wins, the booklet's entry, kept copy and base together.
- **A browser that refuses IndexedDB** (some private modes, blocked site data) keeps everything in local storage, as earlier releases did, and "Your booklets" says so. A store that is full, or fails, is named as such on the page; the work stays for the visit, and the next change tries again.
- **The renderer's keys are its own** and may change between releases: a host's script should neither read nor write them.
- **Several instances on one origin.** The database's name is fixed, `booklet`, and the move reads local storage through `key()` and `length`. A page that ran several independent instances on one origin by wrapping the renderer's `localStorage.getItem`, `setItem` and `removeItem` calls must now also wrap the name given to `indexedDB.open` and local storage's `key()` and `length`, or give each instance an origin of its own.

## The store contract

A host that keeps booklets in a store follows these rules, so a link and a generator agree on what the file is.

- **A link reads one file.** `#/open/<name>` reads `<store>/<name>`, with a plain GET. On a page that declares no store, its links read the default folder, `modules/` beside the renderer. Both are only ever read: the renderer writes to neither.
- **What a copy the reader downloads changes, exactly.** While a reader only answers and keeps entries, the renderer rewrites only the records section at the end of the file, so a comparison of the file before and after shows only what the reader did. Two things a reader can do reach above the records: **renaming the booklet** rewrites the `title:` line in the front matter, and **adding, updating or removing a module** changes the body (the module's fence, the notice box Add a module writes, and any id it renames so it does not clash). A file a reader has changed in those ways is no longer the generator's body.
- **Your file is the truth for a store booklet.** A booklet opened by `#/open/<name>` joins the reader's "Your booklets" as soon as it is read, as a pointer: its name and title, and no copy of its content. The browser keeps a copy only once the reader changes something, and only as a buffer for work your file may not have yet, and beside it a base: the records (answers, entries, drafts; never the body) of the file text the copy is based on, which is the file it last read. Each time the booklet is opened again, by its link or from the list, the file is read afresh, and it is drawn at once, with the browser's copy dropped, when the copy changes nothing of the booklet itself (a rename inside it, a module added or removed: your body wins, so those never reach your file) and either nothing changed in the browser since the base (then your file is drawn whatever it now holds, so work another program put in the file just appears) or the copy and your file hold exactly the same work. This is decided on content alone. So whatever writes the file, a generator included, should **keep the records already in it**: the browser may hold no other copy of a reader's work that was put there by something else.
- **Images are files in the store, beside the booklet.** A booklet opened from the store (by `#/open/<name>`, or from the "Your booklets" entry that came from one) draws its images from the store, and only where the booklet still holds the store's own text. A booklet from the default folder draws its images from that folder by the same rule, only on the page whose folder it is: below, `modules/` beside the renderer is then the store. Each time the renderer reads your file it keeps that text for the visit, and an image is drawn only if the part of the booklet it stands in is exactly the same text as that part of your file. A part is a module (its fence, open line to end line, with its data section) or the opening together with the activities outside every module (everything outside the front matter, the module fences and the data sections, blank lines aside, so a rename or an added module does not change it). So a module the reader added afterwards, one added under an id your file also uses (it replaces that module in place), one removed and added again, a kept copy of an older version of your file that has changed since and not yet been read (the reader is offered "Read the newer file"), and a kept copy from another store or another default folder on the same origin, all show the quiet box and nothing is requested for them. This is checked against the file read on each visit, so it holds on later visits too, and a visit that could not read your file draws no image. Images are drawn where they stand in prose; one written inside a question's wording or an option is not drawn, and only its alt text shows, as plain words, with no box. Any other booklet (one picked from a file, one from the registry, or one from a default folder this page does not have) draws the quiet box and makes no request. A relative path in the booklet is read relative to the booklet's own name. With the store `https://example.org/booklets/`:
  - `![Harbour](images/a.svg)` in `<store>/x.booklet.md` reads `https://example.org/booklets/images/a.svg`.
  - The same line in `<store>/sub/x.booklet.md` reads `https://example.org/booklets/sub/images/a.svg`.
  - In the default folder of a renderer at `https://example.org/app/`, the same line in `sub/x.booklet.md` reads `https://example.org/app/modules/sub/images/a.svg`.

  So put an image where the path in the booklet leads from the booklet's own folder, and serve it with an ordinary `200` and the right bytes. The renderer reads it with a plain `GET` (no credentials, no redirect, 5 MB at most, 15 seconds at most) and checks the bytes against the extension: `.svg` (text beginning `<svg`, after an optional `<?xml ?>` line, comments and a `<!DOCTYPE>` line), `.png`, `.jpg` / `.jpeg`, `.webp`, `.gif` (their own signatures). A path is never requested unless it is made only of letters, digits, `_`, `.`, `/` and `-`, is at most 200 characters, has no empty part and no part that begins with a dot (so no `..` and no `./`), does not start with `/`, and ends in one of those extensions. A path with a scheme, `%`, `?`, `#`, `\` or a space is refused for the same reason. A missing file, one that is too large, one that is not the image its name says, one the browser cannot draw (an SVG with no `xmlns`, a truncated PNG), or a path the renderer refuses, is drawn as the quiet box with a short reason. An SVG is drawn as an image, never inline, so it runs no script and loads nothing.
  - **Your own policy header must keep `img-src blob:`.** The renderer draws each image from a `blob:` URL it makes from the bytes it read, so a header you add that closes `img-src` to anything without `blob:` turns every image into the box (with the reason that the file could not be drawn). The renderer's own policy already allows `blob:`, and a header can only tighten it.
  - **A changed image is read again** whenever the renderer reads the store's file again: opening the booklet again, or "Read the newer file". Within one visit an image (or its failure) is kept once per address.
  - If your server serves only the booklet files (`.md`), it must also serve these image files, under the same store address (or in the same `modules/` folder), or the images show as boxes.
- **Data files are files in the store, beside the booklet.** A data block that names a file (`SPEC.md` section 7, "Rows from a file": a fence line such as `booklet data dashboard.json plots`) takes its rows from that file. A booklet opened from the store, or from the default folder, reads it, and only where the booklet still holds the store's own text for the part the block is in; a booklet from the reader's disk, pasted, dropped or started new reads none, and its views draw a quiet box naming the file. The address is built as an image's is, from the store (or `modules/` beside the renderer) and the file's name relative to the booklet's own folder: `dashboard.json` in `<store>/x.booklet.md` reads `https://example.org/booklets/dashboard.json`. The name is checked first (letters, digits, `_`, `.`, `/` and `-`, at most 200 characters, no part that begins with a dot, ending `.json`). The renderer reads it with a plain `GET` (no credentials, no redirect, 5 MB at most, 15 seconds at most), once for however many blocks name it, and parses it as JSON. So serve each data file with an ordinary `200`, from the same folder rule as the booklet and its images, and keep it small enough to read in that time and size. The renderer writes none. (A host that applies a reader's acts, "Applying a reader's acts" below, writes the file itself, by its own route.)
  - **A changed file is read again** when the page comes back into view, and also when the booklet is opened again. Within one visit and between those moments a file (or its failure) is kept once.
- **A store name is one booklet in a browser.** Opening the same `#/open/<name>` again opens the booklet the browser already keeps for that name, never a second copy. When that booklet holds work your file lacks, it is what opens. The renderer remembers a short fingerprint of the file it last read from that name. If the file you serve now is the same, or is exactly what the kept booklet would write, nothing more happens. If it differs, the reader is offered the newer file, and nothing changes until they press. Pressing it takes the new file's body, and the records are merged place by place against the base: changed in the browser and not in your file, the browser's (work your file does not have); changed in your file and not in the browser, yours (another device's newer answer, an entry it added); changed on both, the browser's, except that something removed in the browser (an answer cleared, an entry deleted, a draft emptied) and changed in your file since stays, with your change. The base is the file as the renderer last read it, so it moves only when a file is read. When your generator has moved an activity to another module, the browser reads the move from the new file's design, by a rule your store's writer can apply to records lines in the same way: work kept under a module the design no longer has goes to the module that now holds the activity of that name (not one outside every module), when every activity your file's records there named lives in that one module (the activities only the browser's unsent work names do not count, since you decided without them); a module that still exists keeps its work, and a module line with no id is no module. Work left under a module the design no longer has is kept as records kept as written under its old records line (SPEC section 8), beside yours kept that way. A copy an older release kept, with no base, is merged once the older way: what holds something in the browser wins, and your file fills in the rest. A booklet that is not a store booklet keeps the reader's own answers, entries and drafts as they are, and nothing is filled in.
- **When a generator rewrites the file,** the generator's body and the reader's records are both kept, because they never overlap. The reader is offered the new file the next time the booklet is opened, and chooses when to read it.
- **The host's server and script are the host's own.** They are not in this repository, and the store is never inside a published repository.
- **A host should say, on its own page, what it serves and who can read it.** The renderer's bar says where a reader's work is kept (in the browser, and in any copy the reader downloads).

## Applying a reader's acts

A booklet can ask a question for each row of a data block, can mark a data field editable, and can offer the reader a row to add and a row to remove (`SPEC.md` section 5, "A question asked for each row", "Editing a field in place", "Adding a row" and "Removing a row"). The renderer only keeps what the reader did, as entries of a `repeat` activity, in the booklet's records. Applying an act (changing a hub's file, running a command) is the host's work, never the renderer's and never the format's. These are the rules a host or an agent that applies acts follows.

**The reference renderer keeps these acts** (0.19.1). An act is one pair in an entry of the activity that holds the view. It writes no data file and nothing to a host. Since 0.20.2 the renderer applies the reader's acts itself to a `booklet data` block written in the booklet (an Add, an Add under a row, a Remove, and an edit in place): the act is kept as an entry, as below, and then written into the block's fence in the booklet's own text, changing no byte outside the fence. That booklet stays on the reader's side, like the rest of the reader's work: in the browser, "Download a copy", and, where the browser has the File System Access API (`showOpenFilePicker`, Chromium) and the booklet was opened through the page's "Open a file I can save back to" button or by dropping the file on the page, written back to that same file once the reader says yes. The page asks once for each file opened in a visit (the browser's permission is for one file, so a second file is asked about too). Nothing about this reaches a host. For a block that reads a JSON file or a host's store the renderer draws no Add and no Remove, and a line that says so; it keeps the entries it finds in the records exactly as written, and leaves them out of every view over kept entries (format 0.20, `SPEC.md` section 13). The rules below are the ones a host or an agent that applies acts follows, and the data it changes may be a file or a `booklet data` block in the booklet's own text.

**What an act looks like in the file.** Each act is one new entry, `{ "<field or question id>": [ { "pick": "<row id>", "a": <the answer>, "was": <the value before> } ], "ts": "<time>" }`, inside the activity's `booklet entries` block (`SPEC.md` section 8). Pressing Enter in an edited field keeps one entry with one pair. A row's Finalize keeps one entry holding that row's pairs, under as many keys as the row has answers (a note and a decision of one row travel together). The `ts` of an act is to the whole second, and two acts never share one (the later moves to the next free second). A number field emptied and kept is `"a": null`. For a made-up orchard:

```json
{"title":[{"pick":"p-orchard","a":"Old orchard","was":"Orchard"}],"ts":"2026-11-07T10:42:00Z"}
{"stage":[{"pick":"p-orchard","a":"resting","was":"growing"}],"ts":"2026-11-07T10:42:05Z"}
{"about":[{"pick":"p-orchard","a":"Eight apple trees.\n\nStakes arrive Friday.","was":"Eight apple trees."}],"ts":"2026-11-07T10:42:09Z"}
{"decision":[{"pick":"b-ladder","a":1}],"reply":[{"pick":"b-ladder","a":"Borrow it first"}],"ts":"2026-11-07T10:43:30Z"}
```

- **Apply each entry once.** An entry is named by its `ts` and the pick of each pair in it (a row's `id`). Remember what you applied; the entry stays in the file, and the renderer never removes it.
- **In place:** an entry whose pair has `was` sets a field the row already had. Find the row by `pick`, compared as text (5 and "5" are one id). Set the field to `a` only if the data's value now equals `was`; otherwise refuse, and record the refusal. This is the stale-page check a dashboard needs, and nothing the reader wrote is lost by it: the kept entry stays, and the reader sees the value now with what was sent beneath it. The renderer compares the data's value and `was` as written, and a choice question's value with its options ignoring case and spaces at either end.
- **Add a row (`$add`).** An entry of the form `{"$add":[{"in":"plots","pick":"j-weed-the-beds-20261108104200","under":"p-orchard","row":{"title":"Weed the beds","stage":"planning"}}],"ts":"2026-11-08T10:42:00Z"}` asks for a new row. `in` is the id of the data block the act is for (the id after `^`; required), so an activity with several blocks says which one to change: change only that block's data (its file and key path, or its inline block). An entry with no `in`, or whose `in` names no data block you hold, is kept as written, neither applied nor drawn. `pick` is the new row's id (a string, or a number when the block's `idFormat` is a bare `{n}`), `under` the id of its parent row (left out for a top row) and `row` the values of the fields the reader filled in; the `id` is not in `row`. Ids are text for every comparison: `pick`, `under` and the ids in the data are compared as text, so 5 and "5" are one id, and so is the `pick` of an in-place edit. Apply it like this:
  - **Apply once, in the order of the `ts`, and remember it.** Keep your own record of the entries you applied (the `ts` and the `pick`); do not decide that an entry was applied from the data alone, because a row you added may since have been removed, and an entry must not bring it back. Do not apply an `$add` that a later entry of the activity (a later `ts`) removes: a `$delete` with the same `in` and `pick`. The newest act on a pick of a block wins.
  - **Already in the data.** If the data holds a row whose `id` is `pick`, at any depth, the entry has been applied: add nothing and say nothing when every field in `row` equals the same field of that row (compared as `was` is, below). If a field differs, it is another row with that id: refuse with "A row with that id exists. Add a part to the id format that tells rows apart (a number, a time or a UUID).", write nothing and leave the entry.
  - **Where it goes.** A top row goes at the end of the block's list of rows. A row under a parent goes at the end of one of the parent's lists. Find the parent by `under`, at any depth: none is "That row is gone."; more than one is "More than one row has that id." Which of the parent's lists: among the parent's fields whose value is a list whose items are all objects, prefer the list that has rows. If exactly one of them has at least one row, it takes the new row (empty lists beside it are ignored, so `"jobs": [...]` with `"tags": []` works). If none has a row and exactly one list is empty, that empty list takes it (the first child of `"jobs": []`). Otherwise refuse ("Cannot tell where the new row goes under this one."): two or more lists with rows, none with rows and two or more empty, or no list at all. A list of plain values is not a candidate, and an empty list is a candidate only in the second step. So a parent with `"jobs": []` takes its first child, a parent with `"jobs": []` and `"tags": []` refuses, and a parent whose child is one object, not a list, refuses. Refuse in each case: write nothing and leave the entry.
  - **The row you write** has `"id": pick` first, then the fields in the order of `row`, in the layout of the row before it in that list, at that row's top level only (nested lines are not copied, and a value that is a list is written on one line, a comma and one space between its items): the same indent, one line staying one line, a row on several lines staying on several lines with the same indent and the same spacing around a colon (`"key": value` or `"key":value`). Rows that share a line: the new row follows a comma and the same spacing as between the previous two rows (one space if there is one row). An empty list gets a plain layout: each row on its own lines, one level (two spaces) deeper than the line the list's key is on (column 2 for a bare list at the root), one space after each colon, a key to a line one level deeper than its row, and the closing bracket on its own line at the indent of the line the list's key is on. Line endings follow the file (a file with CRLF stays CRLF) and every other byte of the data is as it was: no re-sorting, no re-spacing, no change to a byte-order mark or to the blank lines at the end. The comma goes straight after the previous row, then a line ending (or the row's spacing), then the new row; what followed the previous row is as it was.

    ```text
    before                      after an add of b, "row": {"title": "Beds"}
    [                           [
      {                           {
        "id": "a",                  "id": "a",
        "title": "Orchard"          "title": "Orchard"
      }                           },
    ]                             {
                                    "id": "b",
                                    "title": "Beds"
                                  }
                                ]
    ```

    On a single line, `[{"id":"a"},{"id":"b"}]` with an add of `c` becomes `[{"id":"a"},{"id":"b"},{"id":"c"}]`; an empty `"jobs": []` on a line indented 2 becomes `"jobs": [`, the row's `{` at 4 and its keys at 6, then `]` at 2.
- **Remove a row (`$delete`).** An entry of the form `{"$delete":[{"in":"plots","pick":"j-prune","was":{"id":"j-prune","title":"Prune the apple trees","stage":"growing","jobs":[{"id":"j-prune-1","title":"Buy shears"}]}}],"ts":"2026-11-08T10:43:10Z"}` asks to remove a row. `pick` is the row's id and `was` the whole row as the reader saw it, its own fields and the rows under it. Apply it like this:
  - **Find the row** whose `id` is `pick` (compared as text), at any depth. None: it is already gone, so remove nothing and say nothing; this is also the case of a `$delete` that dismisses a row that was only waiting (an `$add` the data never held), whose `was` is `{ "id": pick, …row }` and whose `in` is the add's. More than one: refuse.
  - **Remove it only if it still equals `was`.** Compare the found row, as parsed JSON, with `was`: object keys in any order, strings exactly, numbers by value (`1` equals `1.0`), types strict (`1` is not `"1"`). An integer your JSON reader cannot hold exactly (beyond 2 to the power 53) is compared by the digits the file has, not through a parsed number; if you cannot do that, say so as a limit. If they are equal, remove the row. If not, refuse with "Changed since you drew it." and remove nothing: the reader sees the row again with "You asked to remove this; it changed since."
  - **What goes, exactly.** The row's own text and one comma. If a row follows it in the list, the comma after it goes; if it is the last row, the comma before it goes (it ended the previous row). When the row is alone on its lines, its lines go with it, line endings included, except that when the comma before it goes, the previous row keeps its line ending, so the closing bracket keeps its place. When siblings share a line, the row, one comma and the white space between that comma and the row (or the next row) go, and the other separator stays as it was. Removing the only row of a list leaves exactly `[]`. A child held as one object, not in a list, cannot be removed: refuse and say why in words. Every other byte stays.

    ```text
    remove b, the last row:
    [                       [
      {"id": "a"},            {"id": "a"}
      {"id": "b"}           ]
    ]

    remove b, a middle row:
    [                       [
      {"id": "a"},            {"id": "a"},
      {"id": "b"},            {"id": "c"}
      {"id": "c"}           ]
    ]

    siblings on one line, [{"id":"a"}, {"id":"b"}, {"id":"c"}]:
      remove b  [{"id":"a"}, {"id":"c"}]
      remove c  [{"id":"a"}, {"id":"b"}]
      remove a  [{"id":"b"}, {"id":"c"}]
    ```
- **Controls only where the block can be written.** A host that draws the acts (a plugin, an app) draws no Add, no Remove and no in-place edit on a data block it cannot write: a block it cannot reach (inside a callout or a comment, or a file outside the folder it holds). It says "This data cannot be changed from here." in place of saying the data cannot be read.
- **Do not write what cannot be read back.** If the text you read holds a byte that did not decode as UTF-8 (U+FFFD), write nothing and say "That file is not valid UTF-8, so it was not changed." (a file and an inline block alike). If the new text of a data file would be larger than a reader reads (5 MB), write nothing and say so.
- **The data a host changes.** A file next to the booklet, or a `booklet data` block in the booklet's own text. Use one function for both: it takes the text of the JSON and returns the new text (for a block in the booklet, the text between its fences), and the booklet changes only inside that fence. A block whose data is neither (a source the host does not hold) is not changed, and its entries stay waiting. Write the entry first and change the data afterwards, in one read-modify-save step, as an in-place edit is changed: an entry is applied once, when it is kept, and nothing is retried when the booklet is opened later.
- **A refusal writes nothing and says why in words** (a notice, a line in the host's log). It leaves the entry, and the renderer's display (below) shows the row as it was; the outcome is not stored in the file, so after the booklet is opened again a refused add is shown as "sent, waiting" and a refused removal as "removing, waiting".
- **Append:** a pair with no `was` adds something (a note, a decision, a new item). Add `a` as a new thing. The renderer lists what the data holds under the question as history, then the kept answers newest first with their times, so it shows an added item twice when the host adds it and leaves the entry in the file; a host that prunes applied entries avoids that. An added row (`$add`) is not drawn twice either way: once the data holds a row with the entry's id, a renderer that draws it draws the row from the data and not again from the entry, so a host that leaves an applied `$add` in the file shows no second row; and an `$add` that a later `$delete` of the same pick follows is drawn nowhere.
- **A choice question is a position; an edited `choice` field is words.** For a question (`> [!choice|decision each:requests]`) the answer `1` is the first option of the question as the booklet's own text lists it, which you have in the file you were given. For a field marked `edit: choice` the pair holds the option's own words (`"resting"`), which is the value the field should have.
- **Say what happened through the data.** The renderer shows the outcome from the data it reads: the field's new value, the list's new item, or a row of your own that says "refused: changed since you edited it". The renderer reads the data file again when the page comes back into view (and when the booklet is opened again), and a changed file is drawn in place. What the reader sees follows the display states (`SPEC.md` section 5): the value alone when it equals what was sent; what was sent, marked waiting, while it still equals `was`; the value now with what was sent beneath it otherwise.
- **Pruning is yours.** The renderer keeps every act and removes none. A host that publishes the booklet and its data file may prune the acts it has applied, or keep a log of them (one line of JSON for each act, in a file beside the booklet, is enough), as it likes, and says so on its own page.

## The submit build: sending a reader's answers to one address

Everything above is about the published `booklet.html`, which never sends anything. A host that needs a reader's answers sent to an address, such as a questionnaire service, cannot do it with that file: its own policy allows connections only to the page's origin and `raw.githubusercontent.com`, and a host's header can only tighten that. So it serves a different file, the **submit build**, made from this repository with one command:

```
node submit/build.js --endpoint https://forms-api.example.org/submit --script /host.js
```

- **What it is.** The one-file build (`node test/one-file.js`) with one more script, `submit/submit.js`, placed directly after the renderer's main script. The address is written into the file (`<meta name="booklet-submit">`), and the file's policy gains exactly two things: that script's sha256 in `script-src`, and the address's origin in `connect-src`. `--script` writes the host's own script into the file too, so the file built is the file served. The command prints the file's `sha256`; a host publishes that line, as for `booklet.html`. `booklet.html` is read, never written: the published file is the same before and after.
- **The address.** `https`, with no query and no fragment (plain `http` only for this machine, for testing). Only the host names it, by building the file: nothing in a booklet, a link or the browser's storage can.
- **What the reader sees.** A **Submit** button in the bar, only while a store booklet is open (opened by a `#/open/<name>` link from the store the page declares, or from "Your booklets" after one; not one from the default folder, which is not the store's). Pressing it shows the reader's answers as they gave them, one card per module: each answered question's words above the answer's, in the booklet's own words (an option's words, not its number). Under them, folded shut, **Show exactly what is sent** holds the exact text the press of Send posts. The screen names the address, with **Send** and **Cancel**. An answer no question in the booklet names (a file from an older version of the booklet can hold one) is listed by its id under "Other answers in this booklet", so the list holds everything that is sent. Nothing goes before Send.
- **What is sent.** One `POST`, `Content-Type: application/json`, no cookies, no referrer, no redirect, of `{"recipe": ..., "answers": {...}, "booklet": {...}, "seen": {...}}`. `recipe` is what the host's script named with `BookletSubmit.recipe(r)` (a non-empty string, or an object), else the booklet's own `id`. `answers` holds every module's once-answered questions in one map, keyed by question id exactly as the file writes it, each value as the records section stores it (a choice is the option's position from 1, a scale the anchor's number, text the words). Kept entries and drafts are not sent. If two modules answer the same question id, the screen says so and nothing can be sent. This is the shape the recepture service takes (its `docs/payload-contract.md`). **`seen` and `booklet` (submit build 0.3.0) say what the reader was shown**, because a stored position cannot be read later without the file the reader had, and the body names a recipe and not the file's text. For each answered question, `seen` holds, under the question's id as in `answers`: `question` (its words); for a choice or multi, `options` (the words of the options in the order shown) and `picked` (the words chosen, the reader's own option as they wrote it); for a scale, `anchors` (each `{n, text}`) and `picked` (the anchor's words); for a matrix, `items`, `anchors` and `picked` (one entry per item, `null` where none was picked); and for a widget, `picked` (its summary). A text, lines, number or date question has its `question` only: its answer is already words. All words are plain text, in the booklet's own language, so a French booklet sends French words. `booklet` holds the file's `id`, its `version` where it has one, and its `lang` as the renderer reads it (`en` when the file names none). `answers` is unchanged, so the stored shape is the same, and `seen` adds a few hundred bytes a question (PHQ-9 with nine answers is about 3 KB). The extra top-level keys are accepted and stored by recepture and are never interpreted there. The folded "Show exactly what is sent" shows them.
- **After it is sent.** When the address answers `201`, nothing the reader wrote is removed: the booklet stays open, kept in this browser as it was before Send, and can be downloaded as any booklet. The screen says Sent, with the start of the response id the address gave. The Submit button then reads Sent and sends nothing more until an answer changes; that is remembered in the page only, so after a reload Submit is available again. Because the booklet is kept under its store name, opening that name again opens the kept copy, answers and all: a host that serves the same questionnaire again, and wants it blank, gives it a new name. Any other answer, or none within 20 seconds, says so, and every answer stays, so the reader can press Send again.
- **The host's script** may call `window.BookletSubmit.recipe(r)` (frozen; also `version` and `endpoint`). The submit build hands nothing to a host's script, and its one send is the reader's own press.
- **The address's own rules.** recepture accepts a browser's post from exactly one origin, its `CORS_ORIGIN`, which must be the page's origin. A host that sets its own Content-Security-Policy header must allow the address in `connect-src`, or the send is blocked.
- **Checks.** `test/submit-build.test.js` (the build adds only what it says, and `strip()` gives back the one-file build exactly) and `test/submit-browser.js` (a real browser, against a stand-in for the address, or a running recepture with `SUBMIT_ENDPOINT` set). Neither touches `test/guard.test.js` or `test/pledge-browser.js`, which still guard `booklet.html` and its one-file build.

## Checking that a host serves the real renderer

A host that modifies the file it serves can do anything, with or without this interface, so the check is on the file. Each release's notes carry the `sha256` of `booklet.html`. To print it for a copy:

```
sha256sum booklet.html          # on a Mac: shasum -a 256 booklet.html
```

A host can publish the line it prints (`<hash>  booklet.html`) beside its page so anyone can compare.

**Serve the release unchanged.** From renderer 0.15 a host needs no edit to open booklets by link: put them in `modules/` beside the renderer (`/app/modules/` for a renderer at `/app/`) and serve the released file as it is, so its `sha256` is the release's. A host that adds a `booklet-store` line serves a different file, whose own `sha256` it should publish beside it (in a `SHA256SUMS` file).

**`tools/verify-renderer.py`** (Python 3, standard library only) makes the check for a file or a served address. It prints the copy's `sha256` and says whether it equals one of the lines of a `SHA256SUMS` file (the release notes' `sha256` block saved as a file, or a host's own) or a hash given with `--expect`, and exits 0 on a match, 1 on none, 2 when it cannot read what it was given and 3 when it was given nothing to compare with (it then prints the `sha256` and says on stderr that nothing was compared, so a script that left out its argument does not read a pass). An address is read with one GET: only a 200 counts (a 204 or a 206 is refused), a redirect is followed only to another http(s) address and the address read is then said on stderr, and the whole read has one deadline (`--timeout`, 30 seconds unless given):

```
python3 tools/verify-renderer.py https://example.org/app/ --sums SHA256SUMS
python3 tools/verify-renderer.py app/index.html --sums SHA256SUMS --strip-store-meta
```

`--strip-store-meta` is for a copy made before 0.15: the release plus one `<meta name="booklet-store" content="...">` line. It removes that one line, and only a line that is exactly that tag, before comparing, so the copy matches the release it was made from if, and only if, nothing else in it changed. It prints both fingerprints, the copy's as served and the copy's without the line. A copy with two such lines is refused. A tag written any other way (single quotes, `content` before `name`, capitals, or on a line with anything else) is not removed, and the tool says the copy has a tag that is on no line of exactly that form, so it does not match.

A host that serves `parts/` checks each part the same way, and the two checks chain: `sha256sum parts/mermaid.js` must print the sha256 in the `<!-- PART:` notice inside `booklet.html` (which the core's own checksum covers), so a changed part is noticed even though the core is unchanged. Over http or https the browser makes the same check on every load (the integrity attribute above) and refuses a part that fails it; the command is how a host finds out before a reader does.

## What this does not protect against

- A host that edits the renderer it serves. The checksum above is how that is noticed.
- A flaw in the renderer that lets a hostile page's script run inside the page: such a script could read the page directly. The file's own Content-Security-Policy (above) already stops an injected script from fetching another origin or running inline, and a site's header can tighten it further, so a host's header should allow no connection the renderer and its own script do not need. A policy does not govern WebRTC; the renderer's static guard forbids `RTCPeerConnection` and the like.
